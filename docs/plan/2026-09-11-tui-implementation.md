## 2. 事件层勘察结论（修正施工单「三份分发表」的说法）

施工单说「三份事件分发表」。实测是**两条腿各被写了两遍**，且腿的形状不同：

```
[进程内] Agent ──FnMut(AgentEvent)──► handle_live_agent_event ──► handle_agent_event ──► StreamRenderer
                                       (live_turn.rs:54)          (cli/mod.rs:1215)
                                             ▲ wake.rs 复用这一层
[daemon] Agent ──► RunEventMapper::handle ──► IPC JSON ──► one_shot.rs / wake.rs 各自解码回 AgentEvent
                   (web/event_map.rs:79)                   （两份独立的 IPC→AgentEvent 解码表）
```

- **`AgentEvent → 渲染器` 这条腿已经收敛**：只有 `cli/mod.rs:1215` 一份，被 live_turn / one_shot /
  direct / usage_view 共 24 处调用，且是唯一穷尽匹配（无 `_` 分支）的终端侧表。
- **`IPC kind → AgentEvent` 这条腿有三份半**：`one_shot.rs`（17 处构造）、`wake.rs`（13 处）、
  `cli/output/event.rs:196`（`PublicEvent::from_ipc`，JSON 输出契约），外加反方向的
  `web/event_map.rs:79`（编码器，唯一穷尽 28 个变体的权威表）。
- `remote/interactive.rs` **一处 `AgentEvent::` 都没有**。它模块头写着「事件分发表在这里维护」
  是**过期注释**，表早搬去 one_shot 了。它现在只是外层 REPL 主循环，是消费方不是分发表。

### 2.1 抄多遍抄出来的现存 bug（勘察副产品）

| 缺口 | 后果 |
|---|---|
| `wake.rs` 不处理 `AskQuestion` | 后台任务唤醒里模型提问会挂 |
| `wake.rs` 不处理 `CompactStart/Chunk/End`、`PopStart/End`、`Notice` | 唤醒路径里这些状态不显示 |
| 两边都不处理 `Artifact` | `tool.artifact` 事件在终端侧直接掉地上 |
| `one_shot.rs` 的 `chat.round_usage` 分支自带注释承认「逐请求的计量在 IPC 这一段掉地上」 | footer 整轮不动 |
| `ToolResult` 的「外部输出结束、收回活动区」写了三份且三份时序不同 | 三种残影风险 |

### 2.2 IPC 事件 kind 全集（25 个，解码器的覆盖面）

`turn.started` / `assistant.delta` / `reasoning.delta` / `reasoning.start` / `reasoning.reset` /
`reasoning.part_start` / `reasoning.part_end` / `reasoning.title` / `tool.started` / `tool.preparing` /
`tool.progress` / `tool.output` / `tool.finished` / `tool.image` / `tool.artifact` /
`question.requested` / `queue.consumed` / `queue.removed` / `generation.superseded` /
`chat.round_usage` / `context.compact_start` / `context.compact_delta` / `context.compact_end` /
`context.pop_start` / `context.pop_end` / `context.notice`

其中只有两个需要 async 副作用，不能做成纯解码：
- `tool.image`：data 里是 `asset`（SafeImageAsset）不是 path，要 `render_remote_tool_image().await` 从库里取。
- `question.requested`：要 `question_tui::ask` + 回发 `AnswerQuestion` / `CloseQuestion` / `Cancel` 三条 IPC 命令之一。

### 2.3 收敛的真正阻碍

1. **同步 / 异步分裂（最硬）**：`handle_agent_event` 必须是 `fn`（塞进 `chat_stream_with_control`
   的 `FnMut` 回调），而 IPC 侧的 image / question 必须 `async`。
2. **`Option<&mut LiveReplTail>` vs `&mut LiveReplTail`**：one_shot 要同时服务「`miyu "问题"` 无活动区」
   和「REPL 内有活动区」，签名带 `Option`，于是没法复用 `handle_live_agent_event`。这是 one_shot 和
   wake 明明做同一件事却各写一份的直接原因。
3. `live_turn.rs` 必须把 live 和 renderer 各包一层 `RefCell`（回调持有可变借用 + select 分支也要借）。

**全屏 TUI 天然消解 1 和 3**：统一 select 循环里事件是从 channel 取的，不是回调推的，
可以直接 `.await`，也不需要 RefCell。

## 3. 渲染侧勘察结论（施工单严重低估了这块）

施工单只说「现有 markdown/表格/公式/代码块渲染器改产 `Vec<Row>`」。实测改造面：

| 区域 | 行数 | 施工单提到了吗 |
|---|---:|---|
| `src/render/*.rs`（顶层 9 文件） | 3730 | 是 |
| `src/render/stream/`（StreamRenderer 总入口） | 1623 | **否** |
| `src/render/math/`（LaTeX 三层回退） | 1523 | 否 |
| `src/render/tests/`（断言几乎全是 ANSI 字节串） | ~2900 | 否 |
| `src/cli/repl/tail/` | 1338 | 部分 |
| `src/terminal/kitty.rs` | 505 | 是 |

### 3.1 关键事实

- **约 85% 的渲染函数已经是纯函数**（`&str`/结构体 → `String` 或 `Vec<String>`），
  `command.rs::rendered_lines(width, spinning) -> Vec<String>` 和 `layout.rs` 的 `_for_cols`
  全套是现成的目标形态范式。
- **正文完全不折行**：`render_markdown_line` 返回单行 String，靠终端软换行。只有表格 / 命令块 /
  patch 三处主动折。**全屏 TUI 下这是硬缺口，必须新增折行器。**
- **宽度算法有三套且互不兼容**：`cli::visible_width`（手写 `>= 0x2e80 → 2`）、
  `render::visible_width`、`command_ansi_width`（真 unicode-width + grapheme）。
  统一到 unicode-width 会改变表格 / patch 的现有像素输出，**测试会红一片**。
- **8 处现查 `terminal::size()`**（markdown 的公式与水平线、table、patch、command、wait_spinner），
  改造时都要改成传 `width` 参数。
- **`wait_spinner.rs` 579 行里逻辑只有 ~380 行**，其余是测试。纯函数部分
  （`render_frame_at_width` / `render_block_frame`）直接可用，只是当前是私有 `fn` 要提 `pub(crate)`；
  光标记账层（`tick` / `stop` / `write_spinner_lines` / `clear_spinner_lines*`）全部净删。
- **termimad 只剩一处用途**：`markdown.rs:27` 的 `print_markdown()`，唯一调用链是
  `print_assistant_response` ← `cli/mod.rs:1184` 的历史回放冷路径，而且那条路径的视觉与 REPL
  本来就不一致（default skin vs 自研配色）。**可以删，删了视觉反而统一。**

### 3.2 三个逃不出 `Span` 的东西

| 东西 | 形态 | 处置 |
|---|---|---|
| OSC 8 超链接 | `\x1b]8;;{url}\x1b\{body}\x1b]8;;\x1b\` | 转成 Row 级 metadata，不进 Span |
| kitty 图形 | APC `\x1b_G...\x1b\`，`f=32` RGBA 直传 + Unicode 占位符网格 | 图形序列直接透传给终端，占位符格子进 Row（demo 已验证可行） |
| 公式的 chafa / 半块回退 | truecolor `▀`/`▄` 像素艺术 | 是普通 SGR + 文本，可以正常解析进 Span |

## 4. 第一版走错了：另起一套事件循环

09-11 第一版做成了 `src/cli/tui/`——自己的事件循环、自己的输入线程、自己的
条目模型，与 inline REPL 并行。**这条路是错的**，用户实测三个现象把它戳穿：

| 现象 | 根因 |
|---|---|
| 模型提问后全屏直接退出 | 独立输入线程和 `question_tui::ask` **抢同一个 stdin**。用户在面板上按的键随机落到两边：落到线程的进了 channel，面板收不到；答完回来主循环处理那堆积压按键，里面只要有一个 Ctrl+C 就退了 |
| `/reset` 提示「还没接到全屏界面」 | 另起一套之后 23 个斜杠命令、提问面板、选择器、图片、听写全要重新接一遍，接不完的只能写提示 |
| 重开之后无法交互 | 终端模式（raw / alt screen / 键盘增强）由新写的守卫管，和现有的 `LiveRawMode` 各管各的 |

三个现象是同一个病：**`question_tui`、`inline_picker`、`select` 全都假设自己独占
stdin**，而现有 REPL 的模型保证了这一点（任何时刻只有一个读者）。另起一套就得
给每个组件单独绕一次，每次绕都是新 bug 的来源。

用户的原话是「所有的 UI 效果理论上都应该和 repl 原本的基础上做才对，你现在做的
这个要改的地方太多了」——判断是对的。

## 5. 重做：只换输出层，控制流不动

现有 REPL 本来就有一条干净的分界线，全屏化只需要换这条线**下面**的实现：

| 接口 | inline | 全屏 |
|---|---|---|
| `apply_output_frame(&[u8])` | DECSTBM 受限区写进 scrollback | 喂给终端模拟器，画视口 |
| `suspend()` / `resume()` | 收起 / 重画活动区 | 清屏让出 / 整屏重画 |
| 活动区 | `MoveTo(0, tail_start)` 再打 | **一模一样**，只是 `tail_start` 指向视口底部 |

最后一行是省下大半工作量的原因：活动区的渲染本来就是「定位再打」
（`render_repl_input_with_footer`），全屏下只要把 `tail_start` 指到视口底部，
它一个字都不用改。

**改动一共五处分流**，全在 `tail/frame.rs`：`apply_output_frame`、`suspend`、
`resume`、`clear_screen`，以及 `resume_at` 里算 `placement` 那一步。外加输入路径
上三处插一行视口按键拦截（`input.rs` / `wake.rs` / `one_shot.rs`）。

其余**一行没动**：主循环、23 个斜杠命令、提问面板、选择器、图片、听写、排队气泡。
它们看到的接口没变，所以它们的行为也不会变。

### 5.1 为什么非要写终端模拟器

`screen/term.rs` 是这次重做唯一的大块新代码（~350 行）。不能按 `
` 切行追加，
因为**帧里有光标控制**：

- spinner 每一帧是「上移 N 行 → 清行 → 重画」（`wait_spinner.rs` 的行记账）；
- 命令块的实时输出也是原地刷新的（`CommandLiveDisplay::redraw`）。

只追加的话 spinner 会每帧堆一行，几秒钟就把历史撑爆。模拟了光标动作之后，
这些输出方**一行都不用改**——这正是「在 repl 原本的基础上做」的意思。

只实现 REPL 真会发的那些：SGR、换行、回车、上下左右、定列、清行。没实现的
（滚动区、制表位、备用缓冲切换）在这条路上不会出现，遇到就忽略，最坏是掉一次
样式而不是乱码。

### 5.2 Ctrl+L

全屏下的语义是「把视口顶空」而不是「删内容」——往正文补一屏空行再滚到底，
和终端 `clear` 一个意思，往回翻内容还在。

### 5.3 留下来的东西

第一版里只有这几个模块是有用的，搬进了 `tail/screen/`：

| 模块 | 用途 |
|---|---|
| `ansi.rs` | ANSI ⇄ span 双向转换。解析给选区/折行用，反向给绘制用 |
| `rows.rs` | 行模型、按显示宽度折行、选区取文本 |
| `theme.rs` / `spinner.rs` | 渲染器管不到的外框样式与字形 |

其余约 3500 行（事件层、命令层、悬浮层、条目模型）删掉了。

### 5.4 重做过程里查出的三个根因

都是「输出方以为自己在跟真终端说话」引起的，值得记下来：

| 现象 | 根因 | 修法 |
|---|---|---|
| 打字不回显 | **`ESC[6n` 一轮走查发了 28 次**。`cursor_position_or` 要从 stdin 读应答，把用户正在打的字吞了 | 全屏下这个问题本身没意义（屏幕是自己画的，位置都算得出来），加一个全局标志在 `cursor_position_or` 里直接返回回退值。降到 1 次（Screen 建立之前那次，无害） |
| 用户消息不进历史，回翻找不到 | `commit_submission` / `commit_empty_submission` / `consume_queued` 三处**直接 `write!(stdout)`**，绕过了 `apply_output_frame` | 全屏下改走 `committed_user_messages_frame` + `apply_output_frame` |
| Ctrl+L 清不干净 | 重画靠 `painted` 做 diff，而「清空 painted」填的是空串，**空行画出来也是空串**——diff 认为没变就跳过，旧内容擦不掉 | 加 `force` 标志，全量重画时用哨兵值填充 |

第一条同时解释了第一版「重开之后无法交互」：那时是输入线程、`question_tui`、
`ESC[6n` 三方抢 stdin。

## 8. 第二轮：用户实测报回来的八个问题

用户跑起来之后一次报了八条。**七条同源，两个根因。**

### 8.1 根因一：`suspend` 用的是全屏语义，不是 inline 语义

`/models` 列表、提问面板、`/session` 的选择器——凡是走
「`suspend` → 直接往 stdout 打 → `resume`」这条老路的，全都跑到了屏幕左上角
（问题 4/5/7/8），答完还不留输出（问题 6）。

因为我把 `suspend` 写成了 `Clear(All) + MoveTo(0,0)`。inline 下 `suspend` 的语义
是「**把光标放到正文末尾，擦掉活动区那几行**」——外部输出接着往下写就行。全屏
下照抄这个语义即可：光标移到正文最后一行，只擦活动区往下的行。

`resume` 再置 `needs_clear`：外部输出可能把画面整个顶上去过，逐行 diff 盖不住
那些残留，得整屏擦一次。

另外 `redraw` 不能先 `suspend`——它会置上 `suspended`，而 `paint` 见到这个标记
直接跳过不画，正文就白了。全屏下 `redraw` 直接走 `resume_at`。

### 8.2 根因二：活动区那一笔把整屏顶上去了一行

这条最隐蔽，是靠**在字节流里埋 scroll 标记**才抓出来的（见 §8.4）。

`ensure_repl_space` 在活动区要用到最后一行时，会跳到屏底打个换行把画面顶上去。
inline 下这是对的——顶出去的进 scrollback。全屏下它让**屏幕行 = 缓冲行 − scroll − 1**：
正文最上面那行每帧被挤掉，而程序自己记的坐标没跟着变。后果是点选位置整体差一行，
点第 5 句选到的是第 4 句上面那根空竖条，于是「选不中任何东西」。

修法是一句：全屏下 `ensure_repl_space` 直接返回。屏幕是自己的，最后一行照样能写。

同源还有一处口径不一致：`scroll_by` 按**整屏高**算滚动上限，`paint` 按**正文高**
算，差着活动区那几行——回翻永远停不到底部上方。改成 `Screen` 记住上一帧的正文高，
回翻、点选、绘制都读同一个值。

### 8.3 其余两条

- **问题 1（光标上下跳）**：重画期间不藏光标，它跟着每行的 `MoveTo` 在屏上乱跳。
  `paint` 开头 `Hide`，活动区收尾 `Show`。
- **问题 2（左键选不中）**：原来只接了滚轮，其余鼠标事件吞掉——比 inline **更差**
  （inline 至少还有终端原生拖选）。用户裁定「做自绘选区」，于是
  `screen/select.rs`：按缓冲绝对行 + 显示列记选区（视口一滚屏幕行就变，绝对行不会），
  反显和复制都只认**可复制列**，左边那两格 `┃ ` 装饰不进剪贴板，复制走 OSC 52。

### 8.4 抓错位的方法：把状态埋进字节流

屏幕行和缓冲行对不上，但两边的日志都「看起来对」——paint 的 trace 说 `scroll=37`，
渲染出来的画面却是 38 开头。日志和字节流是两条时间线，**对不上就没法定位**。

办法是在 `paint` 真正开始写字节的地方插一个不可见标记：

```rust
queue!(stdout, Print(format!("\x1b]1337;paint={}\x07", self.scroll)))?;
```

然后在抓下来的流里按标记切帧，一帧一帧喂 pyte——哪一帧用的哪个 scroll、画出来
是哪几行，全对得上，一次就定位到「差一行」。这个标记留在代码里了（`MIYU_SCREEN_TRACE`
才发），下次再有坐标问题还能用。

顺带查出测具自己也在骗人：`drain(master, 1.0)` 这种**固定时长**的读会切在一帧
中间——读了半帧再渲染，看到的是上一帧，断言跟着运气飘。换成
`settle()`（读到连续 0.35 s 没有输出为止）之后才稳定复现。

## 9. 点击展开（`render/blocks.rs` + `screen/expand.rs`）

用户裁定「要做，改渲染器」。

**展开内容不进字节流。** 命令输出动辄几十行，每块都塞一遍既费带宽又把历史撑大；
流里只放一个 id（私有 OSC `1337;miyu-block=<id>`），内容留在进程里按 id 取——渲染方
和全屏后端本来就在同一个进程，没必要绕终端一圈。inline 下 `blocks::enabled()` 为假，
`register` 直接返回 `None`，**一个标记字节都不会多出来**。

三种块接了：

| 块 | 折叠时 | 展开后 |
|---|---|---|
| 思考摘要 | `思考 · 30 词元 · 133ms` | 完整思考正文（`reasoning_text`，本来就攒着，清空前取走） |
| 工具摘要 | `工具×3 ok:3` | 每个工具各自的块（表头 + 主题 + 进度） |
| 命令块 | 砍到 `max_output_rows` | 命令不省略中间、输出不砍前面（以 `CommandOutputTail` 还留着的为准） |

**展开不改缓冲。** `Term` 里那份是「终端真的收到过什么」，改了它光标行号、存档
边界、正在流入的那一行全要跟着算。`screen/expand.rs` 在缓冲之上加一层视图映射：
视图行 = 缓冲行 + 前面所有已展开块撑出来的行数。折叠回去只是把映射撤掉，缓冲
从头到尾没动过。绘制、选区、点击都只认视图行号，`view_row` 是唯一取行入口。

两个细节：

- **起始行要延迟到第一个字符落下才记。** 渲染器会先 `MoveUp` 擦掉旧的几行再重画，
  起始标记发出来那一刻光标还停在块的**下面**。
- **展开内容带上摘要行本身。** 头行是这块的把手，点它才能收起来；只给详情的话
  用户会以为摘要那行被吃掉了。顺带保证展开版永远比折叠版高，视图偏移不会为负。

登记处按**行数**限容（4000 行），不是按块——一块可能是一行摘要，也可能是上百行
命令输出，按块限根本限不住。退出全屏时整个清空。

原地点一下是展开/收起，拖过了才是选区复制：两者共用一次按下-松开，只能靠有没有
拖动来分。

## 10. 第三轮：过程时间线（用户裁定「完全重构」）

用户实测后一次报了十条。**其中五条同一个根因**，剩下的是一次真正的重构。

### 10.1 一个根因吃掉五条

`Screen::resume()` 无条件置 `needs_clear` + `invalidate()`，而 `resume_at` 每帧都调它
——于是**流式输出的每一个 delta 都是 `Clear(All)` + 27 行全量重绘**。后果：

- 光标在输入框里上下鬼畜（问题 3）
- AI 输出时左键拖选卡到没法用（问题 5）

修法是把「重挂活动区」分成冷热两条：

| 路径 | 谁在调 | 整屏擦？ |
|---|---|---|
| `resume_at_own` | `apply_output_frame`、拖选重画 | 不。字节是自己写的，屏幕没被别人动过，走逐行 diff |
| `resume_at` | 其余全部 | 擦。中间可能有外部输出，残留不在自己的账上 |

顺带挖出一件事：**`/help` 这类命令直接 println，从不走 `suspend`**。以前靠「每帧无
条件整屏擦」兜住，加了闸之后它的输出就一直赖在屏上。正解是让它走缓冲
（`repl_help_text()` + `repl_note`）——顺带它现在进历史了，回翻找得到。

### 10.2 其余五条

| # | 现象 | 根因 |
|---|---|---|
| 1 | `/models` 被当消息发出去 | inline 的既有行为（命令也回显）。全屏下改成不回显——命令是一次操作，不是一句话 |
| 2 | 输入区贴着屏底，少一行空 | 上一轮修 `ensure_repl_space` 修过头了：活动区吃到了最后一行。`paint(total_rows + 1)` 把那一行还回去 |
| 8 | 进出全屏时光标在左上角闪一下 | 副屏的光标初始在 (0,0) 且可见。`enter`/`Drop` 都先 `Hide` |
| 9 | 一交互后台进度条就停 | `input.rs` 打字后 350ms 跳过 idle tick。那是 inline 的历史包袱（状态条和活动区两处各自往终端打会写坏帧），全屏由一个画笔按 diff 重画，没这个冲突 |
| 10 | 输入法预编辑框浮在文字上一行 | 全屏下自己算 `input_cursor` 时漏了顶上那根空竖条，少 +1 |

### 10.3 过程时间线（`render/stream/timeline.rs`）

用户要的形状：

```text
  | 工具 运行命令 · 2.4s
  | 思考 思考中 · 320 词元 · 7.5s  …想到哪儿了(每帧刷新)
```

一段连续的过程结束就收成一行，可点开：

```text
  > Worked for 12s · 3 tools · 2 thoughts · 1 err     <- 点它
  v Worked for 12s · 3 tools · 2 thoughts · 1 err     <- 展开后
  | 工具 运行命令 · 2.4s                                <- 再点它
      $ sleep 10 && echo …                            <- 工具的完整输出
```

**没有另起一套渲染。** 时间线接在渲染器既有的三个点上：`finalize_tools_summary` /
`finalize_reasoning_summary` 改成「收成一步」而不是写摘要，三个既有的切断点
（正文开始 / 外部输出 / 回合结束）调 `cut_timeline`。live 区继续由 `wait_spinner`
画，只是喂给它的文本换成了时间线。**inline 一个字节都没变**（`blocks::enabled()`
为假时整套短路）。

### 10.4 嵌套展开：把展开内容再喂一遍终端模拟器

`Worked for …` 展开是时间线，时间线里每项再展开是详情——两层。原来的
`expand.rs` 只支持一层平铺。

巧劲在于：**展开内容本身也是一段 ANSI，里面照样可以带块标记**。把它喂进一个临时
`Term`，拿回来的就是同样的「行 + 块区间」结构，于是展开一层和展开顶层走同一套
代码，递归下去就行。没有新解析器，没有节点树。

### 10.5 覆盖层（`screen/overlay.rs`）

子代理和后台任务**不在正文里就地展开**，点开的是盖住整屏的面板，Esc 关闭。

理由不是好看：它们**还在长**。就地展开的行数每秒都在变，视口跟着抖，主线被冲散。
盖一层就没这些问题——主线原封不动，面板里自己滚，翻页归面板。

两种内容源：

- **子代理**：渲染器把它的内层流水账（它自己的思考、它调的工具）攒进
  `blocks` 的一块里，边跑边灌；面板按版本号发现有新内容就重取。于是「边跑边看」
  是白拿的。
- **后台任务**：日志本来就落在盘上（`JobOverview` 这次带上了 `log_path`），
  面板直接读末尾 256 KB，省掉一条专门的 IPC 分页通道。

`2890493b`（Zen 识别头按 `/zen` 整段路径判）在 main 上而不在本分支，用
cherry-pick 的 `-n` 落到工作区——按规矩不提交，所以它和 TUI 的改动混在同一份
未提交 diff 里。

## 11. 第四轮：时间线成型（九条）

### 11.1 视觉：竖线和 logo 同一列

第三轮把竖线画成了单独一列（`  │ ⚙ 名字`），左边多出一根从头贯到尾的栏杆——
那是画框不是时间线。改成**同列**：logo 是节点，竖线是节点之间的连线，各占一行。

```text
  ⚙ 运行命令 · 2.4s  printf '…'
  │
  ✳ 已思考 · 320 词元 · 7.5s
```

正在跑的那一步**不画 logo**，那一列让给点阵转轮；跑完了才换回静态图标。实现上
是让 `wait_spinner` 的块模式**保留标记前的缩进**——原来它把 `BLOCK_MARKER` 当行首
前缀，转轮只能落在第 0 列。

### 11.2 收起来不能把信息弄丢

第三轮的工具步详情取的是 `tool_block_lines`——那只是「跑没跑成」的统计，**工具真正
吐了什么根本没留**。于是收起来就等于丢了。

修法是在 `ToolStats` 上加两样，只在全屏下填：

- `peek`：时间线那一行右边的单行窥视（命令文本、检索词）
- `detail`：点开看到的完整内容

命令工具尤其如此：全屏下 `CommandLiveDisplay` **不再自己往屏上画一大片**，只当累加器
用，命令文本当窥视，完整的命令与输出留到点开时才看（`timeline_detail()`）。
`ensure_tool_waiting_phase` 里那条 `debug_assert!(command_display.is_none())` 是 inline
的不变式（有命令块就没有转轮），全屏下不再成立，跟着放开。

### 11.3 「回答完问题没输出」的真根因

第三轮以为修好了，其实没碰到点子上：daemon 那条线的提问走的是
`remote/one_shot.rs`，**不是** `handle_agent_event`。面板是盖在画面上的，退场后下一帧
按缓冲重画，问了什么答了什么一起消失。

两条路径都补上 `write_question_exchange`，把一问一答写进缓冲：

```text
  ? 走查用的问题：选一个
  ↳ 甲选项
```

### 11.4 子代理：覆盖层里是它自己的时间线

第三轮的子代理面板是**流水账**，而且根本打不开——内层事件
（`__subagent_reasoning__` / `__subtool_call__` / `__subtool_result__`）
只在 `tool_calls = full` 档才发，默认的 `summary` 档一条都没有，于是
`subagent_overlay_id` 永远是 `None`，那一步退回成普通的就地展开。

改动两处：

1. **Summary 档也发内层事件**（输出截断到 8 KB）。这些前缀只有终端渲染器消费，
   不认识的客户端一直是直接丢掉的，多发不影响它们。调用事件也一起发——面板要靠
   它给每一步掐表，内层事件自己不带耗时。
2. **面板内容改成时间线**，形状和主线一模一样（子代理干的事和主体是同一类事，
   没有理由换一套看法），每一步同样可以点开：

```text
┃ 子代理·走查子代理 · 0.6s  1–3/3
  ⚙ 运行命令 · 0.1s  printf '走查用的命令输出\n第二行\n'
  │
  ✳ 已思考 · 0.5s
```

面板里的展开状态**和正文那边互不相干**，各带各的表——`screen/expand.rs` 的
`layer_*` 那套本来就是「一层内容 + 一份展开表」，覆盖层直接复用。

### 11.5 后台任务面板

状态行钉在活动区里，不在正文缓冲中，所以走单独的命中判断
（`job_strip_start` / `job_strip_rows` 在每帧尾部渲染时记下来）。一个坑：
`background_job_lines` 头一行是空的分隔行，任务从第二行起，直接拿屏幕偏移当
下标会差一位。

内容直接读 `JobOverview.log_path` 的末尾 256 KB——任务跑在 daemon 里，日志本来
就落盘，再造一条 IPC 分页通道没意义。

```text
┃ 走查后台任务 · running  1–10/10
后台第 1 行
后台第 2 行
…
```

### 11.6 测具：桩模型学会了调工具

前三轮的验证都卡在同一件事上：**桩模型只会说话**，工具、提问、子代理、后台任务
一个都造不出来，于是这些路径全靠手测。这一轮给它加了分阶段的工具调用
（按请求里已有几条 tool 结果决定这一轮要什么，免得来回死循环）：

| 开关 | 这一轮要什么 |
|---|---|
| `STUB_ASK=1` | 先弹一个提问面板 |
| `STUB_SUBAGENT=1` | 派一个子代理（它自己会想一段、跑一条命令） |
| `STUB_TOOL=1` | 跑一条前台命令 |
| `STUB_BACKGROUND=1` | 派一条后台命令 |

一个坑：派完子代理之后，**主线**的消息里也留着那段 prompt（在 assistant 的
tool_call 参数里），只按标记认「是不是子对话」会把主线也认进去。得再看一眼
有没有主线那条用户消息。

走查项从 24 条涨到 37 条。

## 12. 第五轮：版式与交互（二十五条）

用户这一轮的原话是「你审美呢？？？」。二十五条里真正的新功能只有几件，其余全是
**版式**和**「这东西看着能点但点不动」**——也就是说前四轮把机制做通了，没把它
做得能用。

### 12.1 一条基准线

之前正文贴第 0 列、时间线在第 2 列、用户消息的竖条在第 0 列而文字在第 2 列——
整屏只有正文不在同一条线上。现在统一：**第 0–1 列是页边距，内容一律从第 2 列起**。

顺带两件事跟着落地：

- 那两格边距**不进选区**（`decoration_width` 把行首空白也算装饰）。复制出来的
  每一行不再带两个莫名其妙的空格。
- 缓冲**会折行了**。`Term` 一直没有宽度概念，长段正文写到屏幕右边就被切掉；
  更隐蔽的是 `Screen::resize` 只在**尺寸变化**时才把宽度交给缓冲，而初值就是
  真实尺寸，于是它一次都没被调到，缓冲整场按默认 80 折。

### 12.2 竖线和 logo 同一列

第四轮把竖线画成了单独一列，左边多出一根贯穿到底的栏杆。改成：logo 是节点、
竖线是节点之间的连线，各占一行。

```text
  $ 运行命令 · 0.9s  cd /tmp/pelican-car && python3 - <<'EOF'
  │
  ✳ 已思考 · 76 词元 · 2.1s
```

正在跑的那一步**不画 logo**，那一列让给点阵转轮；跑完了才换回静态图标。

**每个工具不再是同一个齿轮**：按动作类型归组（`$` 跑命令、`✎` 改文件、`▤` 看
文件、`⌕` 找东西、`⊕` 上网、`❖` 派子代理、`▣` 图像、`✦` 记忆、`☰` 清单、
`¤` 钱、`⊞` 装东西、`?` 问人），认得出"这一步在干什么"比认出具体哪个工具有用。
都挑宽度为 1 的字形——两格宽的符号会把整行推歪。

### 12.3 「准备xx」是前置状态，不是另一种画面

`tool_preparing` 那条粘性提示原本会**顶掉整条时间线**（`tick_spinner` 里它的
优先级最高），于是已经跑完的几步会一起消失，看着就是"新出的一行把旧的覆盖了"。
现在它只是时间线里的最后一行，等真正的工具落下来就被换掉。

### 12.4 收起来不能把信息弄丢

工具步的详情原来取的是 `tool_block_lines`——那只是「跑没跑成」的统计，**工具
真正吐了什么根本没留**。加了 `ToolStats::{peek, detail}`（只在全屏下填）：

| 工具 | 时间线那一行的窥视 | 点开看到的 |
|---|---|---|
| 命令 | 命令文本 | 完整命令 + 完整输出（不再重复 `$ 运行命令×1 ok` 那行表头） |
| 编辑 | 路径 | **补丁 diff**（原来是直接打屏的，既点不开也不在缓冲里，重开就没） |
| 其余 | subject | 工具输出，**JSON 先排版**再给（原来是一行糊到屏幕外的字符汤） |

### 12.5 能点的要看得出来能点

- **悬浮提亮**：鼠标扫过可点的行就去掉 dim。只去 dim 不换底色——时间线本来就是
  "想看再看"的附注，加底色会喧宾夺主。
- **正在想的那一行也能点开**。难点在活动区每帧都是「上移 → 清行 → 重画」：
  每 tick 重发一次块标记的话，登记处会攒一堆同样的块、行号还全是错的。
  两处一起解决——`Term` 在重写某一行时作废该行及其之后的块，渲染器给实时那行
  一个**固定的 id**、每帧只更新内容。
- **输入框里的字能选了**。输入区不在正文缓冲里，所以另记一份「这一屏幕行上是
  什么字」（`render_repl_input_with_footer` 顺手记下画出去的行），选区、反显、
  复制都按这份来。
- **发新消息回到底部**。翻着历史打字然后回车、结果自己刚说的话看不见，是最容易
  让人以为"没发出去"的一种。

### 12.6 浮层：通知条、命令候选、详情面板

三样东西都浮在输入框上方，共用一套细线框画法。

- **通知条**：「已取消」「已停止 1 个后台任务」这类话不是对话内容，几秒后就不再
  有意义。短提示（≤2 行）走浮层、几秒自己消失；长的照旧进正文（`/help` 那种整页
  清单浮起来没法看）。判据就是行数。
- **命令候选**：inline 是在 footer 位置塞一行挤在一起的命令名；全屏有地方，做成
  每条带说明的一小块，Esc 关掉（关的只是"当时那一串"，再打字还会弹）。
- **详情面板不再占满整屏**：按内容高度来，最多吃掉六成，贴着输入框往上开，
  上面那截正文照常画。面板讲的是**某一步**的细节，把主线全遮住反而让人忘了自己
  在哪儿。后台任务的面板还多一条 `x 停止`（新加了 `IpcCommand::StopJob`）。

### 12.7 提问面板不再清屏

`reserve_space` 靠**打换行把画面顶上去**来腾地方。inline 下顶出去的进 scrollback，
全屏下备用屏没有 scrollback——顶出去就是没了，用户看到的是「一提问，正文全被清空，
光标跑到左上角」。全屏下改成只把光标放到底部，面板自己从那儿往上画。

取消提问也不再往正文里逐题写一遍「已取消」：那一下没产生任何内容，把误触变成
永久的一屏垃圾没道理。

### 12.8 图片进缓冲

全屏的正文是从缓冲重建的，**不在缓冲里的东西不存在**——图片直接打屏，下一帧
就被抹掉。现在拆成两半：kitty 的**传输段**发给终端（它要收像素），**占位格**
当普通文字进缓冲，于是重画、回翻都还在；非 kitty 走 chafa 的字符画，本来就是文字。
图片一出也意味着这一段过程到头了，工具信息先收成一行，图片接在下面。

### 12.9 重开 TUI 不再少一块

`turns` 表里**一直存着** `assistant_reasoning`，只是回放的 SQL 没查它。查上，
全屏回放时把它当一步思考喂进时间线（inline 照旧不放——那边一放就是整段，会刷屏）。

`Worked for 0.0s` 也修了：回放没有计时，报个 0 秒比不报还糟，它看着像"这一轮
瞬间就完了"。没有计时就只报做了几件事。

### 12.10 测试：桩模型之外，加一条真模型走查

桩模型能钉住"机制对不对"，钉不住"好不好看"——真模型的思考是长句、工具名五花八门、
输出有长有短，版式会不会崩只有真跑一遍才知道。

`testkit/tui/live.py` 用真模型（默认 `opencodego / deepseek-v4.1-flash`）跑一组
**会把版式压出问题**的任务，逐轮抓整屏，还会去点开时间线、点开里面一步。沙箱只从
真配置里借一个供应商（连 key），会话库、记忆、日志全在 `/tmp` 下另开，不碰 `~/.miyu`。

它当场抓出一个桩模型抓不到的问题：收缩行和正文之间空了**三行**——
`switch_mode(Content)` 给「思考正文直接铺在屏上」那种排版补了两行间距，而全屏下
思考根本没往流里写。

另外修了一个**测试自身**的坑：`blocks::enabled()` 是进程级开关，而 `cargo test`
多线程并发跑，一个用例把它打开会改变同时在跑的别的用例的行为。测试里改成线程局部。

## 7. 预算实测（2026-09-11，release，200×60，桩模型沙箱）

全部功能齐了之后重量一遍（含自绘选区与点击展开）：

| 项 | inline | 全屏 | 差 | 预算 | |
|---|---:|---:|---:|---|---|
| 空载 RSS | ~34 MB | ~34 MB | **−84 … +856 KB** | ≤ +3 MB | ✓ |
| 匿名页 | ~9.7 MB | ~9.7 MB | −52 … +100 KB | — | |
| 空闲输出字节（5 s） | 402 | **0** | −402 | 0 | ✓ |
| 空闲 CPU | 0.0 % | 0.0 % | — | < 1 % | ✓ |
| 按键到回显（中位） | 759.9 ms | **0.06 ms** | — | ≤ 16 ms | ✓ |
| 二进制 | 67 031 960 B（已装 v0.5.0） | 67 073 752 B | **+41 KB** | ≤ +1 MB | ✓ |

**RSS 那一栏给的是区间不是单点**：六次测量（两种顺序各三轮）落在 −84 … +856 KB，
本底噪声就有 ±500 KB 量级，报单个数字是自欺。能下的结论只有
「**在噪声里，离 3 MB 的闸还差一个数量级**」。交换顺序复验（`BUDGET_TUI_FIRST=1`）
是 §7.1 那个陷阱的标准动作，每次报数都要做。

第五轮末（2026-09-12）：inline 先跑 +644 KB，TUI 先跑 +412 KB，
二进制 67 200 536 B（比已装的 v0.5.0 +168 KB）。四闸仍是 4/4。

第六轮末（2026-09-12，含图形直通／统一量尺／正文自折行／贴底排版）：
inline 先跑 **+840 KB**，TUI 先跑 **+1320 KB**，二进制 64.11 MB。空闲输出仍是
0 字节、按键到回显 0.06 ms，四闸 4/4。两种顺序这次同号（都是正的），说明这一轮
确实带进来约 1 MB——离 3 MB 的闸还有三分之二余量。

二进制只涨几十 KB：删掉 rustyline 那 11 个包（nix / fd-lock / radix_trie /
clipboard-win…）抵掉了大部分新增代码。

**空闲输出 0 字节**是结构决定的：没有动画时全屏这条路一帧不画；inline 那 402 字节
是 footer spinner 的 80 ms tick 在跑。

### 7.1 一个把我骗了两轮的测量陷阱

前两轮量到的「全屏比 inline **省** 2.5 MB」和后来的「**多** 14.3 MB」，**都是假的**。

根因：两次 measure 共用同一个 daemon。第一个前端跑完会在 daemon 里留下状态，
第二个启动时要多加载一批东西——**第二个跑的总是多十几 MB，和它是哪个前端无关**。

证伪方法很简单，交换顺序再跑一次：

| 顺序 | 第一个 | 第二个 | 差 |
|---|---|---|---|
| inline → 全屏 | inline 32 440 | 全屏 **47 012** | +14 572 |
| 全屏 → inline | 全屏 32 260 | inline **46 768** | −14 260 |

差值跟着**顺序**走而不是跟着**前端**走，这就结案了。改成每轮重建沙箱与 daemon
之后，两种顺序分别量到 +232 KB 和 +284 KB，方向与量级都一致。

**教训**：对比两个前端时，「共用后端」这件事本身就是变量。没有交换顺序复验过的
对比数字，不能当结论——哪怕它看起来对你有利（甚至**尤其是**看起来对你有利的时候）。

### 7.2 inline 的按键延迟

两种顺序都稳定量到 759 ms，所以不是顺序效应。这是 inline 输入循环的既有行为
（80 ms idle tick + 打字期间 350 ms 暂停动画），**不是这次改出来的**，也没有深查。
全屏这条路是 0.05 ms——事件直接进编辑器再重画，中间没有 tick 要等。

## 13. 第六轮：图形通道与一把量尺（七条）

这一轮用户报的是「表情包会撑出一个大空档」「md 表格渲染有问题」「latex 渲染完全
异常」「图片的**显示大小**你也得考虑」，外加三条交互上的毛刺。看着是四件互不相干
的事，实际只有**两个**根因。

### 13.1 根因一：图形传输段被缓冲吞了

全屏的正文是从 `Term` 这个缓冲重建的，而 `Term` 用 vte 解析字节流。翻 vte 0.15
的状态机：

```rust
// vte-0.15.0/src/lib.rs
0x5E..=0x5F => self.state = State::SosPmApcString,   // ESC ^ / ESC _
State::SosPmApcString => self.anywhere(performer, byte),   // 一个回调都不给
```

APC（`ESC _ … ESC \`）**整段被丢掉**，连 `print` 都不调。kitty 的图形传输走的正是
APC——于是"把图片喂进缓冲"等于把像素扔进下水道：占位格还在（那是普通字符），
kitty 手里却没有对应的图 id，那几十行占位格就渲染成**一片空白**。

用户看到的三个症状是同一件事的三个样子：

| 现象 | 实际发生的 |
|---|---|
| 表情包撑出大空档 | 占位格铺了 N 行，图没到，全白 |
| LaTeX 完全异常 | 同上，公式是图片渲染的 |
| 图片显示不出来 | 同上 |

修法是在 `Screen::feed` 的入口把传输段**分出来直接写终端**，剩下的字节才进缓冲
（`split_graphics`）。占位格留在缓冲里跟着正文一起重画、回翻。

一开始还给传输段留了底、整屏擦之后补发一遍，写完发现是错的，删了：

- 占位符用的是 `U=1` 的**虚拟放置**，图画在哪儿由占位格说了算。整屏擦掉的是
  格子不是图，重画一遍格子图就回来了。
- 一张 90×21 的图是 **500 多个** 3 KB 的分块（`RAW_CHUNK_BYTES = 3072`）。
  留 16 段只能留到最后 16 个分块——补发出去是半张图的尾巴，纯粹的负收益。

顺带被单测揪出一个会切坏字节的边界：找 `ESC \` 的循环写的是 `end + 1 < len`，
没找到收尾时 `end` 停在 `len - 1`，**最后一个字节被吞**。分包正好切在传输段中间
时就会少一个字节。

### 13.2 根因二：全屏下还在拿整屏当量尺

页边距是第五轮加的（第 0–1 列留白），但排版那一侧没人知道这件事，还在
`terminal::size()`。差这两列的后果不是"右边少两个字"，是**多折一次行**：内容排到
第 `cols` 列，缓冲在 `cols` 处折行，续行从第 0 列开始——屏幕左边就冒出半截边框。
用户截图里的 md 表格就是这样：边框断在左边距里。

现在只有一把量尺：`content_viewport()`（列 = `cols - 2`，行 = 正文高 − 1），
全屏之外返回 `None` 走原来的路。所有排版按它算：

| 调用点 | 原来 | 现在 |
|---|---|---|
| `bounded_table_widths` | 整屏宽 − 1 | `content_cols(100) - 1` |
| `render_patch_diff` | 整屏宽 | `content_cols(100)` |
| `command_terminal_width` | 整屏宽 | `content_cols(120)` |
| `horizontal_rule` | 整屏宽 / 3 | `content_cols(72) / 3` |
| `render_display_math` | 整屏 | 正文区 |
| `kitty::display_bounds` | 整屏 | 正文区 |
| `configured_print_size` / `configured_meme_size` | 整屏 × 百分比 | 正文区 × 百分比 |

最后两行是"**显示大小**"那一条：图片默认尺寸是按百分比算的（print_image 45%×35%、
表情包 35%×25%），按整屏算出来的格子数比正文区真能放下的多，一张高图就能把输入框
顶出屏幕。

### 13.3 剩下四条毛刺

- **开发模式的后台子代理，状态行写「开发中」**。`JobKind::Subagent` 加了 `dev`
  标志，`kind_label` 单列一类——那一条是去写代码的，不是去查资料的。
- **流式输出时左键拖选发涩**。`selection_extend` 和 `hover_at` 每次鼠标移动都调
  `invalidate()`，等于让下一帧**整屏重画**；而模型正在快速吐字，帧本来就密。
  选区和悬浮都只改某几行的**画法**，不改内容，逐行 diff 自己能认出来，不需要
  作废全屏。
- **PgUp/PgDn 翻得太快**。原来一次翻一整屏，翻完完全接不上。改成半屏——上半屏
  是刚看过的，视线有个落点。
- `resume()` 只在真挂起过或有外部输出时才整屏擦（这一条是上一轮埋的，这轮一起
  复核过）。

### 13.4 新加的单测

| 用例 | 钉住的东西 |
|---|---|
| `graphics_are_split_out_of_the_buffer_stream` | 没有图的字节流原样放行；多段传输按顺序全挑出；半截传输段整段发走不留在缓冲里 |
| `graphics_leave_no_trace_in_the_body` | `Screen::feed` 真的把分流接上了（接漏了就是一块空白） |
| `body_wraps_itself_instead_of_letting_the_buffer_do_it` | 断在空格、超长词硬断、转义不被切开、宽字符按两格算 |
| `expanded_detail_drops_the_inline_decorations` | `↳` / `│` 摘干净，行首的颜色留着 |
| `a_run_without_timing_reports_what_it_did_not_zero_seconds` | 几十微秒的"计时"不报 `Worked for 0.0s` |
| `edit_step_expands_into_a_diff_without_repeating_the_path` | 改文件那一步点开有 diff，路径只出现一次，宽度按传进去的算 |

### 13.5 真模型走查当场揪出来的四条

这一轮的 §13.1／§13.2 修完，`testkit/tui/live.py` 跑一遍，截图上还剩四个毛病——
全是桩模型抓不到的那类（桩模型的回答短、不带表格、不会拖出两轮之间的时间差）。

**一、正文的软换行还在靠缓冲硬折。**

```text
  notes.md 里本来就是一份三行的待办清单，我没动它：修 niri 的快捷键冲突 / 更新 zen 内核 / 把 1060 那台换 nvidia-580xx-dkms
。要我换成别的内容就说。
```

续行掉回第 0 列。根子在**没有人折行**：markdown 渲染器不折，交给缓冲折，而缓冲
按整屏宽折——正文却是缩进两格写进去的，于是每一行都多出两列。

现在 `indent_body` 折完再缩进（`wrap_display_text`）：认转义序列（正文带颜色，
拿整串量宽度会提前断，切点还可能落在转义中间），能断在空格就断在空格。表格、
代码块不受影响——它们本来就是按同一个 `content_cols()` 排的，宽度正好够。

**二、`Worked for 0.0s`。**

一轮只想了一次就交卷时，摘要报 0.0 秒。因为 `note_start()` 是在**这一步被收进来**
的时候调的，而步是跑完才收——两者正好差出这一步自己的耗时。改成
`note_start_since(spent)`：思考按它自己的计时倒推，一批工具按 `max(各自耗时)`
倒推（并发跑时这是唯一稳妥的下界）。

回放那条路上顺带还有一个：库里存的是"做过什么"，没有计时，可时间线还是会现场
掐一次表，量出来是几十微秒——比零大，照样打印成 `0.0s`。判据从"是不是零"改成
"够不够一位小数"（100 ms）。

**三、正文和输入框之间裂着二十行。**

聊两句，内容在屏幕最上面，输入框钉在最下面，中间一片空白。正文改成**贴着活动区
往上长**：内容不满一屏时上面垫空行（`top_pad`），最后一行正文永远紧挨着输入框。
输入框本身还是钉死在底部——跟着内容上下跳的输入框比空白更难受。

屏幕行 → 缓冲行的换算跟着收口到一处（`body_index`），悬浮、拖选、点击共用它；
垫出来的空行不属于任何一行内容，点上去什么都不选中。

**四、后台任务的汇报贴着第 0 列。**

`⚙ 命令完成 xxx` 那条提示和它下面的汇报正文都是直接打的，没进装订边，也不折行。
现在和别的正文一样走 `indent_body`；图标换成和时间线同一套字体的铃铛
（"有件事发生了"，不是某一步）。

顺带把展开内容里的 `↳` / `│` 摘了（用户：「我觉得是不是没必要有那个箭头和竖线」）：
时间线已经用连线说明了从属关系，再套一层就是同一件事说两遍，两套缩进还对不齐。

### 13.6 测具自己也修了三处

真模型这一轮暴露的测具问题比上一轮多，记下来免得下次再踩：

- **重开那一步只等"静下来"**，而重开要先连 daemon 再查库回放，中间安静好几秒——
  于是抓到的是一屏空白，看着像回放全丢了。改成等到正文真的出现为止。
- **按图标认"哪一行是一步"** 写死了 `$ ⚙ ✎ ▤` 那张表，而图标早换成 Nerd Font 的
  私有区字形了，一行都匹配不上，那一步于是静默跳过。改成按形状认（展开区里带
  ` · ` 的行）。
- **点开之后行号全变了**：正文是贴着活动区长的，展开三行等于整块往上顶三行，
  点开前算的行号在新一屏里指着别处。改成按展开标记 `⌄` 重新定位。
- 顺带：每次跑之前先删掉上一轮的截图。某一步没跑到时留着旧图，看起来像"跑过了
  还是老样子"——这一轮就差点被自己骗过去。

## 14. 第七轮：把那 24 条逐条钉进测具

前六轮的说法是「机制全绿 + 真模型走查没崩」。这对**二十四条缺陷**来说不是验收——
用户报的是二十四件具体的事，走查报的是四十四个别的名字，两边对不上号。

这一轮把 `testkit/tui/run.py` 改成**按用户那份清单逐条断言**：名字带编号
（`item01_…` … `item24_…`），跑完直接打出「用户那 24 条」一节。对不上号的地方
只有两种可能——要么没做，要么没验。两种都得暴露出来。

为此桩模型补了两个阶段：`STUB_EDIT`（改一次文件，验第 12、22 条）和 `STUB_FAIL`
（跑一条 `exit 3` 的命令，验第 21 条）。

### 14.1 逐条断言长什么样

不是"跑一遍看看像不像"，是每条挑一个**只有修对了才会成立**的判据：

| 条 | 判据 |
|---|---|
| 1 | 空输入回车前后整屏**逐字节相同** |
| 2 | 展开后正文行数不减；收起后正文还在 |
| 3 | 悬浮在连线那一行：正文区一个像素都不变；点它：块仍然是展开的 |
| 4/8/23 | 展开出来的每一行，第 0–1 列都是空的（压进页边距 = 某处按整屏宽排版被硬折了） |
| 5 | 展开内容里没有 `↳` |
| 6 | **趁它还在想**点开，隔 1 秒再抓一屏，两屏不同 |
| 7 | 展开那一刻的字节流里有 `ESC[48;5;236m`；点暗底里任意一行，那一片收起来 |
| 9 | 步那一行的图标落在私有区（`U+E000–U+F8FF`） |
| 10 | 提问面板在的时候、退场之后，用户那条消息都还在 |
| 12/22 | 点开改文件那一步看得到 `+走查用的第一行`；`walk.txt` 只出现一次 |
| 13 | 八轮流式输出期间 `ESC[2J` 的次数 |
| 14 | 收起之后，最后一行正文和输入框之间 ≤ 2 行 |
| 18 | 回复中途 Esc Esc：「已取消」出现在**浮层**里 |
| 21 | 失败那一步的行首是 `ESC[31m` |
| 24 | 重开之后收缩行不含 `Worked for 0.0s`，点开看得到思考 |

### 14.2 它当场揪出五个**没修好**的

前六轮以为做完了的事情里，有五件其实是坏的：

**一、候选面板慢一帧（第 15 条）。** `set_command_hint` 是在 `screen.paint()`
**之后**算的，于是它画出来永远晚一帧：打一个 `/` 什么都不出，再补个空格（多一次
按键 = 多一帧）才蹦出来。用户原话「我要打 `/` 空格才会出现覆盖层」，一字不差。
把它挪到 paint 之前。

**二、每敲一个字整屏擦一次（第 13 条）。** `redraw()` 在全屏下走的是
`resume_at`——那是"外面刚往屏上打过东西"的冷路，会置 `needs_clear`。而 `redraw`
是**每次按键**都要调的。AI 正在流式输出时打字，就成了每个字一次整屏重绘。
改走 `resume_at_own` 之后，八轮流式输出期间的整屏擦次数 **55 → 0**。

**三、命令跑挂了不标红（第 21 条）。** `ok` 说的是"工具本身有没有出错"，而
`run_command` 跑了一条 `exit 3` 的命令，工具照样返回 Ok——时间线上它和跑成了长得
一模一样。判据换成命令自己的退出码。

**四、「已取消」进正文而不是通知（第 18 条）。** 中断回复那条路写的是
`apply_output_frame`，直接贴第 0 列进正文；短提示该走的是 `repl_note`（全屏下它
会变成浮层）。

**五、正文和输入框之间的空档还在（第 14 条）。** 第六轮的贴底排版按 `content_rows`
算，而它**不裁光标下面那几行空白**（那是留给"下一段输出"的）。跟随于是一路滚到
光标那儿，屏幕底下空出两三行。改用 `filled_rows`（只看有字的行）。

这一改把 Ctrl+L 顶出去了：它原来靠"灌一屏空行"把视口顶空，而空行现在不算内容。
补了一条显式的**视口地板**（`floor`）：Ctrl+L 记一笔"视口至少能滚到这儿"，新内容
长过它之后自动失效。

### 14.3 测具自己也错了四处（这几条才是真教训）

改测具的过程里，有四个"看起来是产品坏了"的红，其实是测具在骗人：

- **`settle` 在流式输出时会等满 8 秒**。它等的是"连续 0.35 秒没输出"，而模型正在
  吐字时永远静不下来。于是"趁它还在想点开"这一步，等到的永远是这一轮结束之后。
  流式期间点击要把超时压到几百毫秒。
- **两下 Esc 之间隔了一次 `settle`**（也就是 8 秒），超出了 2 秒的待发窗口，中断
  压根没触发——于是"取消"这条断言一直在验一个没发生过的事。连写 `\x1b\x1b` 也不
  行，那会被解析成 Alt+Esc。正解是隔几十毫秒。
- **`render()` 每次都从头重放整条流**。走查后期流有一两兆，一次重放几百毫秒，而
  一轮循环要调好几次——光是"看一眼现在屏幕上是什么"的开销就足够把要等的状态等没。
  改成增量喂。
- **行号在点开之后就失效了**。正文是贴着活动区往上长的，展开三行等于整块上顶三行，
  点开前算的行号在新一屏里指着别处。凡是"点开→再点里面一项"都得按展开标记 `⌄`
  重新定位。

还有一条更钝的：**每次跑之前不清旧截图**。某一步静默跳过时留着上一轮的图，看起来
就像"跑过了还是老样子"——这一轮差点被自己骗过去两次。

## 15. 第八轮：真机像素验收（pyte 看不见的那一层）

前七轮关于图片、公式的结论全是**推的**：「vte 把 APC 丢了 → 分出来直接写终端 →
所以图会出来」。pyte 只还原字符网格，图形协议那一段它一个像素都看不见——
「图有没有真的画出来」只有真 kitty 能回答。

`testkit/tui/kitty_shot.py`：在 cage 的无头输出里起一个真 kitty（不碰用户桌面），
里面跑全屏 TUI，桩模型先 `print_image` 再吐一段带 markdown 表格和 `$$…$$` 的正文，
`grim` 截真像素。

第一张截图就把「推出来的结论」打了：**图没有，公式没有**，只有几个零星的占位符
字形；kitty 自己在 stderr 上喊 `Malformed GraphicsCommand control block ... found: 0xd`。

### 15.1 根因一：`escape_len` 不认 APC

`escape_len` 认 CSI 和 OSC，`ESC _`（APC）落到了兜底分支——**只算 2 个字节**。
于是几 KB 的 base64 载荷被当成正文去量宽度、去折行，折行插进去的换行（再经
`\r\n`）把控制块劈成两半。

这是第六轮"正文自己折行"那一改带出来的：在此之前没人对这段字节量过宽度。
修法是把 APC / DCS / PM / SOS 一起按字符串类序列扫到 `BEL` 或 `ESC \`。
外加一条便宜的保险：带 `\x1b_G` 的那一行一个字都不折。

### 15.2 根因二：组合记号是覆盖不是追加

修完第一条，`Malformed` 没了，图还是不出来——截图上是**每行一个**占位符字形。

kitty 的占位格是 `U+10EEEE + 行号记号 + 列号记号`，一格三个码位。而 `Term::put`
处理零宽字符时写的是：

```rust
if let Some(cell) = line.get_mut(col - 1) {
    cell.ch = ch;          // ← 覆盖
}
```

注释写的是「附到前一格上」，代码干的是**覆盖**。于是每一格只剩最后一个记号，
基字符和行列号全没了。`Cell` 加了一个 `marks: Option<Box<str>>`（只有真带记号的
格子才分配，正文里几乎没有），改成追加。

### 15.3 找根因的办法：把字节流回放进真 kitty

中间卡了一阵——单测说缓冲里的字符是对的，PTY 抓下来的字节流说每行 28 个占位格
都发出去了，可截图上就是不出图。办法是**分层回放**：

1. 只回放「传输段 + 占位行」→ 图出来了 ⇒ 字节没问题、这套无头 kitty 画得出图。
2. 加上 `ESC[?1049h`（备用屏）再回放 → 还是出来 ⇒ 和备用屏无关。
3. 回放**整条**抓下来的字节流 → 图和公式都出来了 ⇒ TUI 的输出是对的。

三步之后才发现真相：**我读的是一张旧截图**。后面几次 `kitty_shot` 因为
`BIN=target/debug/miyu` 是相对路径、而子进程是拿 `cwd=OUT` 起的，daemon 根本没
起来就抛异常退出了，异常打在 kitty 窗口里、外面看不见，旧 PNG 原地不动。

两条教训都记下来：**脚本跑在别人的窗口里就必须自己写日志文件**；
**外部产物要先看时间戳再下结论**。

### 15.4 真机结论

release 二进制，无头 kitty 140×35：

| 看什么 | 结果 |
|---|---|
| 图片 | 出来了，蓝底 + 白/黄对角线 + 四角红点，一个像素不差 |
| 敲一个字触发重画 | 图还在（占位格真的进了缓冲） |
| markdown 表格 | 边框完整，收在正文区里 |
| LaTeX 行间公式 | `E = mc²` 和高斯积分都正常排版 |

至此，那份缺陷清单里「只能在真终端里看」的部分也有像素证据了。

## 16. 第九轮：浮层设计与「工具在前、结果在后」（二十二条）

这一轮用户报的二十二条里，真正独立的毛病只有几件——**四条是同一个根因**，
**五条是同一个设计问题**（浮层）。

### 16.1 一个根因吃掉四条：外部输出把时间线切早了

表情包、搜图、todo、提问——四条报的都是「工具信息跑到结果后面去了」：

```text
› Worked for 5.2s · 2 tools · 2 thoughts
[图]
⌄ 1 tool                     ← 发这张图的那一步，排在图后面
```

根因是 `prepare_for_external_output()` 在**结果落地之前**就把时间线收了。发图的
那一步这会儿还没跑完（`tool.finished` 还没到），于是它只能落进下一段，看着就是
「先出结果，再出干活的人」。

修法是把这类东西排队：渲染器上加一条 `pending_after_timeline`，图片占位格、
todo 表都往里排，`cut_timeline` 把这一段收成一行之后再放出来。顺序于是变成
「时间线 → `Worked for…` → 结果」，和 WebUI 那条时间线一致。

提问不能排队（面板是交互的），改成**反过来**：面板抢屏时只让屏不切线
（`prepare_for_panel`），答案到手把「询问用户」补进这一段，然后才切、才写问答块。

真机截图验到了顺序：

```text
┃ STUB_SCRIPT 把那张图显示出来
  › 2 tools
  [图]
  图打完了。
```

### 16.2 浮层：五条报的是同一件事「它到底在哪儿」

- **通知条**原来贴在输入框上方，正好压住刚写完的正文；而它说的多半是「已复制」
  这类和正文无关的事。挪到**右上角**，时长从 4 秒收到 2.2 秒。例外是
  「要退出请按 Ctrl+D」——它讲的就是输入框的事，留在输入框旁边。
- **后台任务面板没有框**，和上面那截正文糊在一起，分不清覆盖区域到哪儿。加了
  圆角框，左右各留两列。
- **面板每帧都在跳**：高度是按当前内容算的，后台任务每写一行日志面板就长高
  一点、上边沿跟着往上跳。改成**只涨不缩**，开着的时候高度不变。
- **面板里的时间线是散的**：抬头被硬切，续行原样打出去——续行比面板还宽，落到
  缓冲里被硬折，续的续行从第 0 列开始。改成抬头裁一行、续行按面板内宽折行。
- **提问面板浮在半空中**：它从 `anchor_y` 往下画，而 anchor 是按"最多可能占多少
  行"（`MAX_PANEL_LINES`）算的，内容没那么多时底下就空一大截。改成按**这一帧
  真画出来的行数**贴着底边往上顶。顺带修了 anchor 本身：全屏下它去问
  `crossterm::cursor::position()`（ESC[6n），而那条路上 stdin 被输入泵占着，
  问不到就退回假值，面板直接跑到屏幕顶上。

另外，**提问的时候也能回翻了**：`ask_with` 收一个滚动回调，滚轮和 PgUp 只动面板
上面那一截，面板自己那几行不碰。

### 16.3 展开区的底色：只给叶子

用户的原话很准：「Worked for 展开不需要有背景。需要有背景的是里面的 timeline 的
项目」。`Worked for` 展开出来的是一条时间线——给整条加底等于把正文一大片染色。
真正需要"这是一整块"的是点开某一步之后那一片。

同一条还带出一个交互毛病：展开的正文里**空行是不可点的**，鼠标扫过去高亮一闪
一闪，点上去也没反应，可那一片看着明明就是一整块。判据改成"里面还有没有别的
块"：有（时间线）就只认表头，没有（一步的详情）就整片可点、空行也算。

底色也守右边距了——一路铺到屏幕最后一列的话，左边留着两格、右边却顶死，
两边不对称最扎眼。

## 17. 第十轮：子代理那块推倒重来 + 四个具体缺陷

用户这一轮的判词很直接：「子代理的完全不对……算了。我觉得这样设计不好，不要这个
设计了」。

### 17.1 撤掉那扇四行的窗

上一轮给前台子代理开了一扇四行的窗，实测下来三个毛病：线画得不对、里面点不动、
读秒也不对。根子是**它在 live 区里**——live 区每帧重画，不进缓冲，于是块标记、
点击映射、计时全都没有落脚点。

改回单行窥视 + 点开进面板。但窥视换了内容：原来贴的是描述（`开发中·审查 xxx ·
15s  审查 xxx`——同一句话说两遍），现在贴的是**它此刻在干什么**（内层时间线的
最后一步，或者正在想的那段话的末尾），一直刷新。想看全的点开，面板里是完整的
时间线。

### 17.2 面板里的时间线：一次调用只占一步

流水账里调用和结果是两行（`[工具] …` / `[结果] … ok`），原样贴出来同一件事出现
两遍、连线跟着翻倍。改成把结果**盖回**那一步（给它标上 ok/err，失败换成红叉），
续行归进那一步的正文。

顺带三件：

- 每一步登记成块，行里带标记——面板里也能点开看全文，和主线一个规矩。块 id
  **按位置复用**：日志是只增的，每次重读都新登记一批的话，登记处几秒就刷爆，
  而且用户点开的那一块会在下一次刷新时变成另一个 id、当场合上。
- 子工具的摘要先过 `tool_subject`。原来直接贴 JSON，面板里全是
  `{"command": "cd /very/long/path && …"}`。
- 后台**命令**的日志没有"步"可言，按时间线排会变成每行一个节点、行行之间一条
  连线——那是把日志排成了梯子。没有标签行时原样折行。

### 17.3 选文本发涩的真正来源

上一轮只做了事件合并，还是卡。真正的开销在展开层：`layer_len` / `layer_row` /
`layer_in_expansion` / `layer_hit` 每次都把**所有块**走一遍。聊久了缓冲里攒着几百个
块，而这几个函数是每行每帧都要调的——一帧就是上万次比较，AI 正在输出时两边叠在
一起，手上就是"好卡"。

加了两条快路：一个块都没展开时直接返回（最常见的情形），以及 `layer_hit` 在没有
展开时**二分**（块按起始行有序）。

### 17.4 其余四条

| 条 | 修法 |
|---|---|
| 3 | 提问面板底下留一行空，别贴死屏幕边 |
| 4 | 「加载中」那个点阵贴着屏幕左边，而它下面每一行正文都从第 2 列起——全屏下给它加上装订边 |
| 5 | 图片上面多一行空、下面少一行空：收缩行后面本来就带一行空，排队时不该再补；而图**下面**那一行一直没有 |
| 6 | 链接还是点不开——markdown 链接在屏幕上只露一个标题，目标藏在 OSC 8 里，而缓冲一格只存字符和样式，没地方挂链接。给 `Cell` 加了 `link`（`Arc<str>`，一行几十格共享一份） |

**图标也换了**：MDI 那一段（原子 U+F0768、机器人 U+F06A9）在用户的字体里是空的，

## 18. 第十一轮：输入泵才是「发涩」的真凶

### 18.1 两轮都找错了地方

前两轮为"AI 输出时选文字发涩"改过两次：先是合并鼠标事件（少画几帧），再是给展开层
加快路径（少走几百个块）。用户回来的话是「依旧发涩，**AI 输出一停就没事了**」。

后半句才是线索。输出停下来之后走的是**空闲循环**，那边一次把就绪事件全抽干
（`while event::poll(ZERO)`）；而回合跑着的时候走的是另一条泵：

```rust
let mut input_tick = tokio::time::interval(Duration::from_millis(16));
...
if !event::poll(Duration::ZERO)? { continue; }
let event = event::read()?;   // ← 一个 tick 只取一个
```

拖一下鼠标一秒上百个事件，而这儿每 16 ms 只取一个——队列只进不出，选区落在光标
后面越来越远。改成鼠标事件就地抽干，第一个非鼠标事件仍交给原来那条路。

**A/B 实测**（桩模型，流式输出中猛发 80 个鼠标事件再敲一个字符，量那个字符多久
出现在输入框里）：

| | 输入延迟 |
|---|---|
| 一 tick 一个事件（原来） | **1295 ms** |
| 鼠标事件一次抽干 | **17 ms** |

这条已经钉进走查（`item02_input_keeps_up`，阈值 500 ms）。

顺带记一笔证伪：这一轮还做了"逐行跳过没变的行"（给每行记版本号，画之前先比对）。
它确实省下了每帧三十几行的重排，但**对这个症状没有贡献**——A/B 出来字节数
416352 vs 416990、CPU 1930 ms vs 1890 ms，都在噪声里。逐行 diff 早就把没变的行
拦在写出去之前了，省的只是算的那一下。留着它是因为省的是真的，但别把它当成
这条 bug 的解释。

### 20.2 浮层开着的时候有两支画笔在抢

前台子代理一点开面板就"疯狂鬼畜"、底部在面板页脚和输入框 footer 之间反复横跳，

下一次真轮询把它原样带了回来。改成按**时间**放（5 秒，守护进程一秒一轮，留几轮
余量）。

这条是靠**字节流**抓出来的：闪一下在屏幕上只存在几十毫秒，按渲染后的画面采样根本
抓不住，而"又画了一遍"那一笔一定留在流里。走查里新增
`item05_ctrlc_no_strip_flash`——停完之后三秒内，流里不该再出现那个任务名。
为了让这条测得到，桩模型加了 `STUB_BG` 记号（消息里带它就当场再派一条后台任务，
不看阶段表）。

## 21 第二十一轮：九条

用户那九条，外加"上一轮修完反而坏了"的三条回归。

### 21.1 并排跑的工具共用一个块 id → 所有工具行都点不开

第二十轮把"正在跑"改成**一个工具一行**，却让每一行都挂着同一个 `live_block`。
展开层按块 id 找内容，同一个 id 出现好几次时它会把那一块插好几遍——行号、偏移、
点击命中全跟着错位。表面症状是用户说的"现在所有工具行都无法交互展开了"，连带
子代理那一行也点不开面板。

改成 `live_tool_blocks: BTreeMap<事件名, 块 id>`，一个工具一块；子代理那一行优先
指它自己的面板，面板还没登记出来时退回自己那一块（别让它变成死行）。

钉住它的是 `parallel_running_tools_each_get_their_own_block`：两个工具并排跑时，
两行的块 id 必须**不同**且各自非空。上一版代码在这条上直接红。

### 21.2 选完松手，反显就没了

`input_select_finish` 是 `take()` 掉选区——手一松高亮就消失，看着像"刚选的又被
取消了"。正文那边的选区松手之后是留着的，两处该一致。加了 `input_dragging`：
按下时开、松手时关，选区留在屏上，零宽度的单击才清。

走查里原来只断言剪贴板（OSC 52），所以这个回归全绿溜过去了。新增
`reverse_cells()`——直接读 pyte 的 `reverse` 属性，也就是屏幕上真正的反显；
判据是"拖动时有反显，松手后不少于拖动时"。

### 21.3 Esc 退出模型选择器却说"已更新"

`inline_fuzzy_select` 的 Esc 语义是"就这样，完事"（和 `q` 一样），不是"取消"——
所以 `run_models_for_session` 自己会打一句"未做修改"。问题在调用方：
`interactive.rs` 不看结果，**无条件**再补一句"会话模型已更新，下一轮生效"。

`run_models_for_session` / `run_models_global` 改成返回 `Result<bool>`：真=真的改了。
Esc、勾选没变、非终端只打清单，全是假。

### 21.4 面板里工具那一步点开是空的

`log_step_detail` 原来只在"抬头被裁过"时才把抬头补进详情——短命令点开就是一条
空带子。而工具那一步的正文常常**就是**抬头本身（命令、路径、检索词）。改成抬头
无条件给全：行里那份是裁过的，详情里这份是完整的，不算说两遍。

还缺真正值得看的东西：工具吐了什么。`__subtool_result__` 本来就带着 `output`
（`clip_detail` 截过），只是 `subtool_summary` 写流水账时丢掉了。现在摊成
`[结果]` + 若干 `[输出]`（最多 24 行），面板那边把 `[输出]` 挂到刚才那一步的详情里。

### 21.5 工具次数与词元不涨

`report_stats` 原来只在子代理**跑完**时报一次，而面板恰恰是它跑着的时候才开着的。
上一轮改成"每轮报一次"，还是差一格：一轮里并排调五个工具是常事，那五个跑完之前
标题上一直是上一轮的数。

现在每调完一个工具就报一次，走**新的前缀** `__subagent_metric__`：
`__subagent_stats__` 是要落进流水账留底的，中途的量报一秒来好几次，落进去会把
面板里那条时间线撑满。格式是"机器读的在前、制表符、人话在后"——和内层工具事件
一个写法。

### 21.6 状态行上时间左边要有一串量

`JobEntry`/`JobOverview` 加 `metric`，后台子代理的日志桥收到 `__subagent_metric__`
就 `jobs::set_metric`，状态行渲染时贴在时间左边。命令类任务没有词元这个概念，
那儿就是空的。

### 21.7 子代理的开头是「差事」

面板里原来全是它自己的动作——思考、调工具——唯独没有"它被要求干什么"。那件事只有
派它出去的那一轮知道，而隔十分钟回来看这个面板的人是没有那一轮的。

- 前台：`write_tool_call` 认出子代理时往它的流水账里插第 0 步，正文是完整 prompt。
  `trim_subagent` 把这一步钉在最前面，不跟着老步骤一起被挤掉。
- 后台：派出去之前往日志头上写一行 `[提示]`，换行折成 `\u{1}`，面板那边拆回来。

### 21.8 思考那一行不上绿，绿给它的正文

第二十轮把"收起来也是绿的"当成一致性改了，用户看下来是反的：抬头绿、正文白，
像"把手比内容还重要"。规矩定死：**抬头一律暗色，绿色只给展开出来的思考正文**，
主线和两种面板（前台块 / 后台日志）三处一个样。

### 21.9 测具这一轮踩的四个坑

- **瞬间跑完的东西测不到**。桩模型的子代理内层原来跑一条 `printf`，几十毫秒就
  完了——"面板标题上的数会不会涨"、"状态行有没有量"这类断言根本采不到样。加了
  `STUB_SUBAGENT_COMMAND` / `STUB_SUBAGENT_BG_COMMAND` / `STUB_SUBAGENT_BG_ROUNDS`，
  让它慢下来、多跑几轮。

## 22 第二十二轮：五条

### 22.1 重开之后思考行没了

`turns.assistant_reasoning` 只留得住**最后一回合**那份思考（`ChatResult.reasoning`
是最后一次请求的）。想完就去调工具、最后一回合直接交卷的那种轮，那一列是空的
——回放时间线里就没有"想"这一步了（真模型走查实录：实时 `Worked for 4.4s ·
1 tool · 1 thought`，重开变成 `› 1 tool`）。

流水账（`turns.replay_journal`）本来就是"按顺序发生了什么"，只是当初按"只有实时
视图需要"把 reasoning 一起丢了。现在加一条 `ReplayEntry::Reasoning`：挨着的思考
事件并成一条，单条封 1 KB（整份流水账只有 8 KB，让思考占满会把工具条目挤出去）。
回放时按它在流里的位置喂回去；流水账里没有思考的老轮，还是拿那一列兜底。

inline 不受影响：那边回放用 `ReasoningDisplayMode::Hidden`，思考块进去就被丢掉。

### 22.2 前台子代理的浮层：点不开，而且不刷新

两个根因，都在"块登记处"这一侧。

**登记处被自己刷爆**。`subagent_lines` 每次发布都给每一步**新登记**一块，而它一
小段思考就要走一遍（一秒好几次）。登记处按行封顶 4000 行，很快就满；淘汰挑的是
**id 最小**的那个——子代理自己那块覆盖层在它跑起来的第一刻就登记了，id 最小，
于是总是第一个被端掉。面板于是不再刷新、行也点不开。

两处一起改：
- `subagent_lines` 改成**按位置复用**块 id（后台任务面板早就是这么做的）。
- 淘汰改成挑**最久没碰过**的那个（`Entry.touched`，登记／更新／读取都会刷新）。
  一直在用的块不该被当成最老的。

**跑着的那一行没裁**。`timeline_running_tool_lines` 不裁行，而窥视是子代理内层的
思考末尾，长度不受这一行控制：它能把行顶出屏幕，缓冲把它折成两行，块的起止就跨了
行——点上去命中不到。`step_line` 一直是裁的，这条路漏了（用户原话：开始刷新思考
窥视之后就没法交互了）。

### 22.3 抬头和窥视之间用 `·`

原来是两个空格，而同一行上「名字 · 秒数」那半截用的是 `·`，两种分隔读起来就是
断句不齐。统一成 `PEEK_SEP = " · "`：主线的工具行、子代理面板的每一步、「差事」、
「已思考」、「思考中」、「询问用户」全都走它。

### 22.4 后台子代理面板：抬头没有量、右边框不齐、思考窥视不动

- **抬头带上量**：`job_panel_title` = `标题 · 状态 · 量`。状态行上有、面板里没有
  说不通。
- **右边框不齐**：面板里的排版一度按**整屏宽**算（`Overlay::cols` 传的是屏幕宽），
  而框只有屏宽减六。行长出框外 → 画的时候硬裁一刀 → 右边那根竖线参差不齐。
  收口成 `panel_inner_width()`：构造、抬头裁剪、正文折行、绘制全用它，尺寸变化时
  面板也跟着重排（原来一直不跟）。子代理面板那一侧同理——它的步是渲染方按**整屏**
  宽排好的，进面板就要折成两行，改成按 `panel_step_width()`（屏宽减六）排。
- **输出要洗干净**：`[输出]` 那几行是工具的**原始输出**，带转义序列、回车、制表符。
  面板按纯文本算宽度，算出来的和真实占宽对不上，边框跟着歪。写日志时就洗掉。
- **思考窥视取末尾**：面板里原来给的是最新那一段的**开头**，一整段落下来之后这一
  行就再也不动了。改成 `peek_tail`，和主线一个口径——想到哪儿了比想过什么更有用，
  而且它一直在走，正好是"它还活着"的指示。

### 22.5 子代理的量进会话累计（用户那个疑问）

答案：**进，但要等它跑完**。子代理的用量记在审计会话行上（`sessions` 表里
`kind='subagent'`、`parent_session_id` 指向发起它的会话），而 `session_token_totals`
的 SQL 里本来就把它们 SUM 进 Σ 了。问题只是那一行**跑完才写**——一个子代理能跑
好几分钟，那几分钟里 Σ 纹丝不动。

改法不是提前建审计会话（那会改审计的语义），而是在 footer 上加一份**实时加数**
`TokenMeter.live_extra_tokens`，两路来源：

- 前台：渲染方记下每个子代理**至此**烧了多少（`__subagent_metric__` 的第二段，
  纯数字），`running_subagent_tokens()` 求和；回合收尾时清零——那时调用方会从库里
  重读 Σ，审计会话已经落盘，留着就是算两遍。
- 后台：`JobOverview.metric_tokens`，状态行刷新时按"还在跑的子代理"求和。

**并行不会鬼畜**：记的是每个子代理各自的**最新值**而不是增量，几个一起跑也只是
求和；而且 `update_live_extra_tokens` 返回"变没变"，没变就不重画——不然那条一秒
调一次的 `set_jobs` 会让整条尾巴一直抖（用户预判到了这一点）。

### 22.6 Ctrl+C 之后输入框冒出代表按键的怪字符

取消那条路**不交接终端模式**：`LiveRawMode` 守卫在半路 drop，会关 raw、收回括号
粘贴与焦点上报、并**弹出键盘增强协议**（`ESC[<1u`）；紧接着编辑器那边又推回去。
在这一来一回之间按下的键，终端按旧协议发、crossterm 按新协议解，解不出来就当普通
字符塞进输入框。正常收尾那条路一直是交接的，几条提前 return（Ctrl+C、run.cancelled、
run.failed、断线、Ctrl+D 脱离）全漏了。

判据看字节流：取消之后那一段里不该出现 `ESC[<1u`。

### 22.7 测具这一轮的两个坑

- **滚轮那条只看正文变没变**。原来还想拿面板自己的范围指示（`48–55/55`）当对照，
  可后台任务一直在写日志，那个数自己就会动——拿它当"没被滚到"的证据是假的。
- **抬头刷新那条要趁刚点开就测**。等下面那些步骤走完，任务多半已经收工、面板

## 25 第二十五轮：五条

### 25.1 浮层把内容往上推

`paint_overlay` 里跟随的落点是按**面板上方剩下的高度**算的
（`content_rows - top`），等于把正文整体往上顶了半屏。面板是**盖**上去的，
盖住谁谁就先看不见，不该把底下的东西挤走。改成按**没有面板时**那个高度算
（`content_rows - body()`）。`overlay_click` 和 `scroll_above_panel` 三处口径统一
——不一致的话翻上去之后下一帧又被拉回来，或者翻回底部停在一个 paint 下一帧还要
改的位置上，屏幕跳一下。

### 25.2 diff

四件事：

- **去掉竖线**。`   1 + │ body` → `   1 + body`。符号那一列已经把增删说清楚了，
  竖线只是把正文往右推两格、和别的展开内容对不上列。这是 `render_patch_diff`
  那一份共用代码，inline / shellhook 一起改（一份代码一个长相）。
- **首尾空行掐掉**。渲染器为了在整段输出里留呼吸空间自带首尾空行，而时间线那边
  `step_detail` 也会在上下各留一行——两份加起来就是两行空白。
- **颜色**的真凶不在 diff 自己身上：展开区那层暗底（`paint_expansion_bg`）把每个
  span 的底色一律盖成 236，diff 的 `+`/`-` 两条底色带当场被洗成一片灰。改成
  「自己已经有底色的留着」。
- **时机**：`live_tool_lines` 现在直接吐 `stats.detail`。原来要等这一段过程收完
  （模型开始说正文）才看得到 diff，"用了工具"和"看得到它改了什么"之间隔着整段回复。

### 25.3 子代理：正文、词元、收成一行

- **正文一个词一行**。思考和正文都是逐 delta 来的，而日志桥只攒了思考。抽出
  `accumulate_stream` / `flush_stream_buffer` 两个小函数，两种流共用。
- **词元多算了一遍**。`chat_with_tools` 的循环里每一轮都 `add_usage_or_estimate`，
  而 `run()` 收尾又加了一次——**最后一轮算了两遍**。末轮的 prompt 里装着整段对话，
  一个跑三十来步的子代理能因此抬高一大截。收尾那次改成只在「一次都没记上」时用
  估算兜底（供应商压根不报用量的情形）。**这条在 main 上就有，不是这次改出来的。**
- **开口说正文就把前面那段过程收成一行** `⌄ Worked for … · N tools · M thoughts`，
  点开还是那几步——和主线 `cut_timeline` 一个规矩（用户提议：把主体相同的逻辑放到
  浮层里）。两条路各实现一份：前台走事件（`collapse_subagent_segment`），后台读
  日志（`collapse_log_segment`）。「提示词」那一行钉在最前面不参与收缩——它说的是
  "要干什么"，不是过程。
- 顺带：`content()` 改成 Summary 档也发（同 `reasoning`），前台面板才知道"它开始
  说话了"。

### 25.4 看不到 todolist 的 tag 行

`todowrite` 跑完那条路会 `self.tool_stats.clear()` 把**整批**清空。inline 那边是对的
（表已经就地画出来了，再留一行「任务列表×1 ok」是同一件事说两遍），全屏下却把这
一步连同**同一批里别的工具**一起抹了。改成全屏下只收状态、不清表。

### 25.5 后台任务工具换图标

`job`（显示名「后台任务」）→ U+F0572 `md-view_list`。码位先用 fontTools 反查了
名字，确认是列表图标、且和 todo 那个（U+F03A）不撞。

## 26 第二十六轮：六条 + shellhook 跟进

用户报了五条全屏的毛病，外加一条：shellhook（单次 `miyu "…"`）还是老的
`~ 工具×1 ok / ↳ 主题` 卡片，要跟着时间线走。

### 26.1 diff 靠右

`push_patch_diff_line` 的行号栏是固定 `{:>4}`：一位数的行号前面空三格，再叠上
展开区自己的四格缩进，整段 diff 比旁边的思考正文、工具输出都往右缩了半截。
改成先把每一行算出来、按**这一段里最大的行号**定栏宽（最少两格）。inline 那条
`render_patch_diff` 走的是同一个函数，一并变窄。

### 26.2 diff 要等回合结束才看得到

`__patch_preview__` 其实早就进了 `stats.detail`——问题在 live 区：`timeline_live`
只给**正在跑**的那一行挂块标记，已经跑完的步骤在 live 区里是死行；只有
`cut_timeline` 把整段收成 `Worked for …` 时才给每一步登记块。于是编辑跑完到模型
开口之间，那一步点不开，用户看到的就是"diff 要等 AI 输出完"。

修法：`Step` 上加 `block`，**收进时间线那一刻就登记**（`settle_new_steps`），
live 区每帧重发同一个 id；`cut_timeline` 复用它而不是再登记一次——展开状态跟着
走。

### 26.3 Ctrl+C 漏出 inline 的命令卡片

`finish()` 和 `release_transient_output()` 无条件 `command_display.commit()`，那是
inline 下"把命令卡片落进正文"的写法。全屏下命令块只是个累加器、从不自己上屏，
可回合在命令跑到一半时收尾（Ctrl+C／断线），`finish()` 照样 `commit`——
`$ 运行命令×1 运行中 / ↳ cmd / │ 输出` 整块漏到全屏画面里。

`release_transient_output` 同样会漏：同一批里第二个工具一来、或一张图要落，正在跑
的命令就被提交出去。两处都按 `timeline_enabled()` 分流；`finish()` 那条把它此刻的
样子记到统计上（`interrupt_command_display`），随后 `timeline_push_tools` 看到
"收进来时还没跑完"就标成**已中断**（红色打叉，抬头带「已中断」）。

### 26.4 命令展开没有流式输出

`live_tool_lines` 只看 `stats.detail / peek / progress`，命令的实时输出在
`command_display` 里根本没读——点开就是那一句窥视。改成命令工具从
`command_display.live_detail()` 取（完整命令 + 此刻为止的输出），每 tick 重算一遍，
展开着的那一块跟着输出一起长。`CommandLiveDisplay::timeline_detail` 和它共用一份
排版，只差"要不要结算尾巴上那半行"。

### 26.5 子代理面板两条

**后台**：`is_tool_step` 把「正文段」和「`⌄ Worked for …` 收缩行」也当成工具步。
子代理开口说过话之后，Full 档下 `run_command` 的 `[结果]` 没有对应的 `[工具]`
行（调用事件不发），往回找"最近一个没结果的工具步"就找到了收缩行——给它盖了个
`ok`；跟着的 `[输出]` 又贴到正文段里，面板里就是一段话底下拖着几十行裸 grep
输出（截图）。判据加上 `!speech && glyph != SUMMARY_GLYPH`，这种结果自己立一步。

**前台**：`log.speech` 一直挂在面板最底下。子代理说完一段再接着想、接着动手，
新的「思考中」和后面的步骤排到了它**上面**。正文是时间线上的一件事，按时序占位：
新的思考／工具一来就把说过的话封成一步（`seal_subagent_speech`，`Step::speech`），
只有**还在说**的那段留在底下。`collapse_subagent_segment` 的起点相应改成"最后一段
正文之后"——收缩的是产出之前的过程，产出不收。

### 26.6 shellhook：静态时间线

shellhook 走的是 `remote/one_shot.rs` + inline 渲染器（`live = None`），所以它的
形状就是 inline 的 `tool_summary_live` / `CommandLiveDisplay` 那套。新加第三种形态
`timeline_static()`：**不是全屏、但 stdout 是终端、工具按摘要档显示**时启用
（管道里仍是老摘要；Full 档不动）。`timeline_enabled()` = 全屏可展开版 ∪ 静态版，
时间线的取数、抬头、连线、图标全共用；只在"能不能点开"上分岔：

- 每一步跑完当场落进 scrollback（`commit_static_steps`），live 区只留
  `│` + 转轮行——整段留在每帧重画的 live 区里只会闪，超过一屏还擦不干净；
- 能展开的东西就地印在那一步底下：命令印**输出尾巴**（最多 `command_output_lines`
  行，命令本身已经在那一行上，不再印一遍）、编辑印 diff、报错印
  `STATIC_ERROR_LINES`（8）行输出；跑成的普通工具只留那一行，思考只留
  `已思考 · N 词元 · Xs`；
- 跑着的命令在转轮行底下露出输出尾巴（`LiveRow::tail`）；
- 没有 `Worked for …`——点不开的把手只是一行废话；这一段结束只空一行；
- 缩进：全屏的两格页边距是全屏的概念，静态版贴第 0 列（`indent()`），和原来
  那块卡片同一个位置。

顺带：`settle_tool_batch` 收完一批立刻把转轮挂回去。原来收进去的那一刻 live 区是
空的，要等下一次 `reasoning.start` 才重新出现——网络那一秒里整条时间线闪没了又
闪回来，全屏一直有这个毛病，只是没人报。

### 26.8 第二批反馈：连线贯穿、命令行底下的流式行、右移

用户实测第一版之后的六条：

- **连线断得很严重**（静态版）。正文那几行原来缩进四格、上下各空一行，连线在每一步
  的正文处断掉。改成每一行都从连线穿过（`  │ ` 前缀，`rail_prefix`），紧贴抬头不空
  行；超出行数时第一行就是 `│ ⋮ 已省略较早输出`。`gap_owed` 那套欠空行的逻辑随之
  删掉——没有空行就没有欠不欠。
- **命令不展开也给一行空间流式刷新**（全屏）。跑着的命令在抬头底下露最新一行输出
  （`LiveRow::tail`，全屏 1 行、静态版 `command_output_lines` 行）；块的结束标记放在
  尾巴之后，于是点开时展开内容把抬头和那一行**一起**换掉。
- **报错**：命令的输出照印，但整段红（`static_detail(width, failed)`）、行数和跑成时
  一样受限；其他工具报错**不印**任何输出——多半是一团裸 JSON，印出来只会丑。
  `STATIC_ERROR_LINES` 删除。
- **整体右移**：静态版也退两格（`indent()` 恒为两格），转轮那一档的 margin 跟着退。
- **Ctrl+C 延迟**：沙箱里量到按下后 21 ms 转轮行消失、123 ms 出「已取消」
  （`testkit/tui/round26.py` 的 `t_ms_*`），daemon 侧是 `select!` 立刻掐断 + SIGKILL
  进程组，路径本身不慢。体感慢更可能是 **debug 二进制**整屏重绘慢（这次按用户要求
  部署的是 debug），要验证的话编一次 release 对比。
- 顺带修一处隐患：`clip_to_display_width` 裁行时把裁掉那截里的转义序列一起扔了——颜色
  复位丢了会把后面整行染色，块结束标记丢了会让那一块开到天边。现在裁完把剩下的转义
  序列补在省略号后面。

**shellhook 吞掉回合错误**：fish 钩子里 `fish_command_not_found` 那两条路是
`miyu --shell-intercept … 2>/dev/null`，`main.rs` 打到 stderr 的
「错误: no LLM provider/model endpoint succeeded …」整个被吞。`run_shell_intercept`
现在自己把错误红字打到 stdout，再带退出码、空正文返回（`main.rs` 见正文为空不复述）。

**rebase 到 main（sandbox 提交之上）**：临时 WIP 提交 → `git rebase main` → 只有
`tools/vision/print.rs` 一处冲突（取 main 的 `run_chafa` 重构；工作树里那段
`--probe-mode ctty` 是它的前身）→ `git reset HEAD~1`。TUI 侧没有 `Workspace` 残留，
`/sandbox` 的提示走 `repl_note`（≤2 行进通知条、长的进正文）不用改。

### 26.9 第三批反馈：转轮进左边距、问答融进时间线、/reset、表格

- **转轮挪到左边距**（用户提议：`<转轮><logo><抬头>`，logo 就不用被顶掉了）。
  正在跑的那一行现在是 `⠋ $ 运行命令 · …`：块标记前不再放缩进，转轮落在第 0 列，
  工具 logo 留在第 2 列，跑完只是转轮消失。准备态、思考中、`运行中` 兜底行都带上
  各自的 logo。什么都没在跑时是 `⠋ │`——转轮压在连线上。
- **省略标记随命令报错标红**：`static_detail`（静态版）和 `live_detail`（全屏展开）
  按 `status == Error` 把 `⋮ 已省略较早输出` 和每一行输出都染红。
- **问答融进时间线**（静态版）。原来面板退场时自己留一块「已回答 N 个问题」（带自己
  的竖条），落在「询问用户」那一步**上面**。现在 `question_tui::ask_with` 多一个
  `leave_summary`：静态版传假，面板整个擦掉、光标回到面板顶上；
  `timeline_push_question` 改成收整个 `QuestionResponse`，答案写成那一步的正文
  （`│` 空行、`│ 已回答 3 个问题`、`│ 标题：答案`、`│` 空行），从连线穿过。
- **`/reset` 不清屏**（全屏）：ResetConversation 之后补一次 `clear_screen`
  （视口顶空，往回翻还在）。
- **表格比视口宽、边框折到下一行**（全屏）。根因：`VIEWPORT_COLS/ROWS` 只在第一次
  `paint` 时登记，而开全屏后紧接着的**历史回放**在那之前渲染——`content_viewport()`
  还是 None，表格按整屏宽排，加两格装订边就比屏幕宽一格。`Screen::enter` 现在当场
  登记（行数先估、首帧 `paint` 纠正）；回放帧的宽度也改按视口。

### 26.10 第四批：命令预览四行、子代理浮层三件

- **全屏跑着的命令预览给四行**（`LIVE_PREVIEW_ROWS`），超出时第一行换成
  `⋮ 已省略较早输出`，和落地之后那块一个颜色（`live_tail` 现在自己带省略标记，
  静态版也一并有了）。
- **浮层里没有「准备xx」、跑着的内层工具没有活动行**：内层 runner 的流式回调原来
  只转发思考和正文，`ToolCall` 块（工具名已解码、参数还在流）直接丢。现在发
  `__subtool_preparing__<name>`（只发 `preparing_phase` 认得的慢参数工具，和主线一个
  规矩）；面板收到就露一行 `准备编辑 · 1.2s`，收到 `__subtool_call__` 换成
  `运行命令 · 运行中 · 1.2s · <窥视>`，结果回来再换成那一步。后台面板走日志：
  桥写 `[准备] <id>\t<phase>`，解析时只有**末尾**那一行才算数（别处的都是过去式，
  收尾时丢掉）；末尾那个没有 `[结果]` 的 `[工具]` 标成 `· 运行中`。
- **收缩会丢内容**：两个面板的收缩行原来都只把抬头串成一段文字，工具输出、思考全文
  在收缩那一刻就没了，点开收缩行也再点不进去。改成收起来的每一步各自登记成块——
  前台在收缩那一刻登记一次（内容已定），后台按 `(收缩行位置, 步位置)` 复用 id
  （`fold_blocks`）——点开收缩行是时间线，时间线里每一步再点开才是正文，和主线
  `cut_timeline` 一个形状。
- **后台面板没有 Worked for**：流水账里没有时间戳。桥现在记下每次 `__subtool_call__`
  的时刻，结果回来时把耗时写进 `[结果]` 行（`运行命令 ok · 1.2s · ls`）；面板解析
  出来挂到那一步（抬头照主线写成「名字 · 秒数 · 窥视」），收缩时把各步耗时加起来
  当这一段的 Worked for（思考没记时，所以是下限）。

### 26.11 第五批：后台面板只剩一个 Worked for、提示词绑着思考、中断轮不回放

- **后台面板永远只有开头一个 Worked for**：`collapse_log_segment` 的起点一律取
  "提示词后面第一步"，第二次 `[正文]` 到来时把上一个收缩行、上一段正文连同新的
  几步全卷进一个收缩行。改成和前台一样：起点是**上一段正文之后**，没说过话才是
  提示词之后。
- **提示词绑着思考**：提示词那一行原来是时间线的第一步，和思考之间连着线，看着
  像一条线上的两步。两个面板都改成独立抬头（`PanelEntry::Header`）：不连线、
  和第一步之间空一行、不参与收缩。
- **重开 TUI 少最后一轮**：`session_replay` 只取 `status = 'completed'`，被 Ctrl+C
  掐断的那一轮虽然进了上下文、`/history` 里也有，重开后正文里却没有。现在
  `interrupted` 也回放：正文尾巴上那段给模型看的 `<system-reminder>` 去掉
  （`interrupted_prefix`），末尾标一行「已中断」。

### 26.12 第六批：面板的空行与连线次序、Worked for 丢失、浮层抖动

- **后台面板提示词底下少一行空**：抬头后面补上空行。
- **正文和时间线"反了"**：正文之后的下一步原来画连线，看着像收缩行属于上面那段
  话。连线现在只连**相邻的两步**；步和正文之间、提示词和第一步之间都空一行——
  收缩行紧跟着它产出的那段话（主线「Worked for → 正文」的次序）。
- **Worked for 丢失（主线）**：`write_tool_call` 只给命令和子代理掐表，普通工具的
  `elapsed` 是 None；一段里只有普通工具（比如被打断的「搜索图片」）时收缩行就是
  光秃秃的 `1 tool · 1 err`。现在每个工具都掐表、跑完冻结。
- **Worked for 丢失（后台面板）**：桥原来只写 ≥100ms 的工具耗时，几个快工具加不
  出一个 Worked for；思考完全没记时。现在耗时再短也写，`[思考]` 行前面带上这段
  想了多久（`[思考] 1.2s\t正文`，制表符隔开，老日志没有也认），收缩时一起加。
- **后台任务完成时开着的浮层抖一下**：`follow_wake_run` 打「后台任务完成」表头走的
  是 inline 那套 `suspend` + 直写 stdout + `resume_at`——全屏下直写进不了缓冲，
  `resume_at` 又整屏擦掉重画。全屏改走缓冲（`apply_output_frame`），表头用铃铛
  图标、退两格。

### 26.13 第七批：面板转轮、收缩行展开的排版、裸 JSON 窥视、`0.0s`

- **子代理浮层没有转轮**：面板内容是一段静态 ANSI（前台是块内容、后台是日志折出来
  的行），没人每帧重写它。加一个占位格 `LIVE_SPINNER_CELL`（私有区 U+10FFFD）：
  面板里正在跑／正在准备／正在想的那一行由 `panel_live_step_line` 生成，占位格在
  第 0 列、logo 在第 2 列（和主线同列）；`paint_overlay` 每帧把它换成当帧的点阵
  字形（`Screen.overlay_spinner` 记帧号，80ms 换一帧）。跑完的行不带占位格。
- **Worked for 底下的缩进与时间线不对**：收缩行的块内容原来走 `indented_body`（当正文
  缩进四格、铺暗底），而收起来的那几步本来就是整行、带缩进、连好线的时间线。
  `Step.fold` 标出收缩行，`step_detail` 对它只出 `[抬头, │, 各步…, 空行]`；
  前台 `collapse_subagent_segment` 不再对步骤行做 `undecorate`（它会把行首的
  `│ ` 当 inline 装饰剥掉）；后台 `fold_detail` 同样改成抬头 + 连线 + 各步。
- **窥视是裸 JSON**：没有主题规则的工具（AUR 查询之类）三处都退回了原始
  `args`。新加 `tool_peek`：主题 → 命令文本 → `args_peek`（参数对象里的标量值按
  原文次序用 ` · ` 串起来，数组/嵌套跳过）→ 什么都没有就不带主题。`serde_json`
  的对象按键名排序，所以按键在原文里的位置排，`{"action":"info","package_name":
  "zzq"}` 出来是 `info · zzq`。前台 `subagent_tool`/`subagent_tool_started` 与后台
  日志桥 `subtool_summary` 都走它。
- **`0.0s`**：不是 bug，是所有工具都掐表之后（26.12）几十毫秒的步被印成 `0.0s`。
  统一走 `reported_seconds`（至少十分之一秒才报）：主线步标签、子代理面板的工具
  步与思考步、后台面板 `with_elapsed`/`step_head`；交到后台的子代理（立刻返回）
  不报秒数。收缩行的总耗时照样把这些短步算进去。

单测：`tool_peek_spells_out_arguments_instead_of_raw_json`、
`the_fold_opens_into_a_timeline_not_an_indented_body`、
`a_running_subagent_step_carries_the_spinner_cell`、
`a_subagent_step_without_a_subject_rule_spells_out_its_arguments`、
`a_quick_tool_step_does_not_report_zero_seconds`、
`a_log_fold_opens_into_a_timeline_and_the_running_step_spins`。

### 26.14 第八批：浮层三件（转轮/准备态、Worked for 箭头、命令展开）

- **浮层里的转轮与「准备xx」**：转轮本身（26.13 的占位格）是转的，测具抓两帧
  确认换帧；两个真问题在别处。一是面板内容只在事件到来时重生成，「准备执行 ·
  0.0s」和标题上的秒数停在上一次事件那一刻——`tick_spinner` 的时间线分支现在
  每 100ms 调一次 `refresh_subagent_panels`，把还没收尾的面板重灌。二是**主线
  REPL 的回合被 daemon 当成网页回合**（常驻连接不带 origin tty），子代理进度走
  Full 档，而 Full 档下 `tool_call_detail` 对 `run_command` 不发 `__subtool_call__`
  （怕 inline 画两遍）——面板里最常见的工具从来没有「运行中」那一行，「准备执行」
  一路挂到结果回来。现在这条事件每个档、每个工具都发；inline Full 档收到命令的
  call 事件时不画命令块（结果那一条整块画），网页端本来就是 call 记着、result
  落卡。顺手：参数开始流（preparing）那一刻就把这一段思考结算成一步（原来要等
  结果回来，「准备执行」一直压在「思考中」上头，思考的耗时还把工具跑的时间算了
  进去）。
- **Worked for 左侧箭头**：收缩行合着是 `›`、点开（块内容第一行）翻成 `⌄`——主线
  就是这么翻的，两个面板原来一直是 `⌄`。前台 `FOLD_GLYPH_CLOSED` + `fold_line_open`，
  后台 `LogStep.glyph` 仍用 `⌄` 当身份（`is_tool_step`/收缩计数靠它），只在画行时
  换成 `›`。
- **命令展开**：后台面板每一步尾巴上拼着 ` · ok`（主线、前台面板都不写 ok，跑砸了
  靠红色和打叉）；展开正文第一行是把抬头（`运行命令 · 5.3s · echo …`）再说一遍。
  现在 `LogStep.subject`（`[工具]`/`[结果]` 行 ` · ` 后面那段）当正文第一段，空一
  行，再是输出；前台 `subagent_tool` 的正文同样改成「主题 / 空行 / 输出」，去掉
  正文里那个 `$`（它是抬头上的图标）——和主线那一步点开一个样子。

- **顺手（测具截图抓到）**：后台面板日志末尾的 `[统计]` 行被当成「还没回来的那个调用」
  标成运行中、挂上转轮（`⠏ 工具调用 3 次 · 运行中`）。`is_tool_step` 现在也排除
  `STATS_GLYPH`。

测具：`testkit/tui/round26.py` 新增 `scenario_panel_spinner`（开着浮层抓两帧：
转轮换帧、标题秒数上涨、跑着的行有 logo）；`scratchpad` 里的 stream-json 事件倒
出法（`miyu --output-format stream-json <prompt>` 对着桩 daemon）是坐实「没发
`__subtool_call__`」的手段。
