# 一个字节的重量：Miyu 的上下文与缓存设计理念

> 本文沉淀 v7 计划（`cache-and-prompt-plan.md`）背后的设计哲学，以及 2026-08-06
> 实测批次中得到验证的全部处理技巧。计划文档回答"做什么、按什么顺序"，
> 本文回答"为什么这么做"。文中每一个结论都有字节级实验背书，出处一并写明。

## 引言：为什么一个聊天机器人要在乎缓存

Miyu 是一个长期在线的角色扮演 agent。她挂在 QQ 群里陪人聊天，也在终端里帮人
修 Arch，还要维护自己的记忆、日记和好感度。这决定了她的负载形态和一次性的问答
工具完全不同：**会话是以天计的，上下文是以十万 token 计的，而每一轮对话都要把
之前的一切重新发给模型一遍。**

这是 LLM API 的本质：它是无状态的。你以为你在"继续对话"，实际上每轮都是把
系统提示词、工具定义、全部历史、当前输入从头到尾重放一次。一个 100k token 的
会话聊十轮，名义上就要处理一百万 token 的输入。供应商的前缀缓存（prefix cache）
是唯一的解药——如果这一轮的请求和上一轮的请求在开头有一段完全相同的前缀，
服务器可以直接复用那段前缀算好的 KV 状态，只对新增部分做 prefill，价格通常是
全价的十分之一，速度快一个数量级。

于是问题变成：**怎样让每一轮请求，都是上一轮请求的严格延续？**

这个问题看起来是工程细节，实际上牵动 Miyu 的整个上下文架构。本文就是这条线
索的完整展开。

## 一、缓存不懂语义，只懂字节

先建立一个反直觉的事实：前缀缓存的匹配单位不是"意思"，是字节（更准确地说，
是分词后的 token 块，DeepSeek 和 vLLM 系都是 64 token 一块）。两段在人类看来
一模一样的上下文，只要有一个字符的差异——一个时间戳变了分钟、一个工具描述
多了个空格、一个 JSON 键换了顺序——从那个位置开始，后面的一切都要全价重算。

而且损失不是从差异点开始那么简单。我们在 DeepSeek 上做过一个判别实验（B3）：
构造一个请求，只改动 tools 数组里**第一个工具描述中的一句话**，其余几万 token
纹丝不动。结果命中数是零——不是"工具之后全 miss"，是**连排在工具前面、完全
相同的 system prompt 都一并失效**。因为 DeepSeek 的服务端模板把工具渲染在
提示词极靠前的位置，一处分叉，满盘皆输。

这个实验给 Miyu 定下了第一条铁律，我们称之为**前缀即契约**：

> 相同的会话状态，必须产生逐字节相同的请求前缀。

它听起来朴素，执行起来却要动到每一个往上下文里塞东西的模块。所有非确定性的
内容——时间、随机数、探针结果、异步加载的模型元数据——要么彻底不进前缀，
要么在进入前缀的那一刻被冻结。序列化路径必须唯一：同一份消息，不允许存在两条
会产生不同字节的渲染代码。这不是洁癖，是因为缓存的账本上，语义等价一文不值。

## 二、大前提：不许动 Miyu 的灵魂

在讲技巧之前必须先划红线。Miyu 首先是一个角色扮演体验，其次才是一个工程系统。
v7 计划的第一句话就是"不影响 Miyu 现有功能和语义"——一切缓存优化，模型看到
的"意思"必须前后一致。一个为了缓存命中率而变得健忘、迟钝或出戏的 Miyu，
是本末倒置。

这条红线派生出两个结构性的设计：

**三份内容分离。** 同一轮对话在 Miyu 内部存在三个版本：`raw_content` 是用户
原始的话，记忆系统、联想检索、日记生成只读它；`display_content` 是界面展示用
的；而工程附加物——运行时上下文、发送者元数据、化石化的瞬态消息——走独立的
通道（`context_messages` 等 sidecar）。这个分离的意义在于：**缓存工程再怎么
折腾字节，都不会污染 Miyu 的记忆。** 她日记里记下的是"Shorin 问我 Linux 能不能
玩幻想神域"，而不是一坨夹着 XML 标签和时间戳的工程噪声。

**权限由代码承担。** 提示词里的任何标签、任何"你是管理员"的声明都不承担鉴权
职能——发送者是谁、有没有权限，由执行层拿着真实的 principal 判定。这让我们可以
放心地把各种上下文块挪来挪去、化石化、重排，而不必担心某次重排让一段旧的元数据
"提权"。上下文布局是缓存的领地，安全不在里面。

在这两个分离做好之后，剩下的一切优化都获得了自由：我们可以对字节做任何事，
因为字节层和语义层、安全层已经解耦了。

## 三、Append-only：把上下文当成一本只增的账本

如果说"前缀即契约"是静态约束，那么 append-only 就是动态约束，也是整个理念的
核心。它可以概括成两句话，恰好与 Kimi 官方缓存文档的表述逐字一致——这不是
巧合，而是两边独立撞上了同一个物理现实：

> **追加不要插入；注入了就别删。**

### 插入的代价：一个时间戳的案例

Miyu 每轮会往上下文里注入一条 `<runtime now="…分钟级时间戳"/>`，让模型知道
现在几点、在哪个目录。最初它被放在当前用户消息**之前**。这个位置看起来无关
紧要——反正都在请求尾部——但它制造了一个每轮必然发生的分叉：本轮的实时请求
是 `[…历史, runtime, 用户消息]`，而下一轮重放历史时 runtime 被丢弃（它是"瞬态"
的），变成 `[…历史, 用户消息, 助手回复, …]`。于是下一轮的请求与服务器缓存里
的条目，恰好在 runtime 所在的位置分道扬镳——**上一轮辛辛苦苦算过的整段内容，
从用户消息开始全部作废。**

修复只是把它挪到用户消息之后。在终端场景里用户消息只有十几个 token，收益看
似微小；但在 QQ 群聊里，用户消息里裹着整段群聊记录，是几 KB 的大块——位置
错误让这一大块永远进不了可复用的前缀。一个消息的顺序，就是这么值钱。

### 删除的代价：化石化的由来

比插入更隐蔽的是删除。Miyu 的每轮请求带着一批"瞬态"内容：运行时上下文、
联想记忆、图片提示、表情包提醒、QQ 发送者元数据。传统做法是这些东西用完即弃
——下一轮重放历史时它们不再出现，理由是"节省 token"。

但算一笔账就会发现这个直觉完全是反的。一条瞬态消息一二百 token，删掉它，
每轮省一二百 token 的**账面输入**；但它造成的分叉让后面几千、几万 token 的
前缀**从命中价跳回全价**。省一块钱的动作，花掉十块钱。

于是有了**化石化**：凡是发送过的瞬态内容，写进 `turns.context_messages` 存档，
重放时逐字节回放，永不删除。旧的时间戳就像地层里的化石——它说"那一轮的时候，
现在是 19:20"，模型读得懂，语义无损，甚至还多了点时间感。每轮的化石成本是
常数级的一二百 token，换来的是整段前缀的连续性。

化石化上线后我们抓包验证：连续两轮请求共享 84% 的字节，第一个分叉点精确落在
上一轮 prompt 的末尾——这是当前实现的理论最优位置（残余的分叉是上一轮模型
回复的重渲染，属于下一阶段的工作）。

### 唯一的例外

Append-only 的账本也有翻页的时候：compact。上下文逼近窗口上限时，压缩是
不得不做的一次"自愿冷启动"。理念对它的要求只有一条：**单调**。水位线只能
向前推进，压缩产物一旦写下也进入账本，不许反悔、不许中段改写。冷启动的成本
靠摊销消化——真正要避免的不是冷启动本身，而是**计划外**的冷启动：指纹变更
不再删历史、每 turn 至多一次工具变更，都是在堵计划外冷启动的口子。

## 四、工具目录的三角困境与 stub 解法

工具定义是前缀里最大的定时炸弹。Miyu 有八十多个工具，全量加载要几万字符；
懒加载（用到再加载）省 token，但每次加载都会改变 tools 数组——而第一节已经
证明，tools 一变，满盘皆输。我们实测的 hybrid 模式会话：第一轮里模型调用
`load_tools` 加载了四个游戏查询工具，紧接着的第二个请求缓存命中为零，就是
这个机制的现场。

这里存在一个三角约束（linux.do 上有一篇独立推导出同样结论的讨论）：**严格
原生调用、稳定前缀缓存、真正按需加载——没有供应商配合时，三者只能取其二。**

Miyu 的选择是 stub 模式：所有懒工具以"真名 + 一句话摘要 + 宽松参数壳"的形式
**常驻** tools 数组，数组从此会话内字节恒定；需要完整参数契约时通过 `load_tools`
以工具结果的形式按需获取——工具结果落在对话尾部，不碰前缀。放弃的是参数的
语法层校验（enum/pattern 降级为文本描述），而 Miyu 的执行层本来就是 handler
自行取参，这个损失恰好为零。三选二，选得毫无痛感。

实测效果：hybrid 模式下工具循环的轮内命中是 0%，stub 模式下是 95%～99.8%，
并且上下文越大越接近 100%。

## 五、实测优先于文档：一次侦探过程

以上原则听起来都能从原理推出来，但这一节要讲的是：**光有原理会死得很惨。**
供应商文档所描述的缓存行为和真实行为可以相差一个数量级，而且真实行为里有
文档完全没有提及的机制。

起因是一个用户观察：第一轮显示命中 76.5k，第二轮同样的问题却几乎全 miss。
我们按教科书排查了所有客户端嫌疑——tools 稳定性、消息顺序、流式与否、中段
system 消息、消息数量——每排除一个，就冒出一个新的反例。最后把 Miyu 发出的
请求逐字节抓包、用 curl 原样重放，**同样的字节复现了同样的失败**：客户端
无罪。再用加了 nonce 的副本重建全新的链，同样的结构却 100% 命中。

至此真相浮出水面，DeepSeek 官方的缓存有一套任何文档都没写的行为：

- **处女链全量持久**：一次性写入的线性长链立即完整落入持久层，五分钟后照样
  全额命中——这正是基准测试和大文档问答看到的美好世界；
- **会话链退火**：逐轮增量生长的对话链，每个请求只多持久化约 1k token。
  我们在十二个数据点上看到命中头部以每请求 +1k 的速度爬行；
- **热窗口随负载浮动**：深层前缀只在"最近被触碰过"的窗口内可复用，晚高峰
  实测不到 25 秒，深夜能到 5 分钟以上；
- **写入是异步的**：上一请求刚算完，1.5 秒内跟进的请求会 miss，6 秒后稳定；
- **逐字节相同的精确重放走另一条索引**，任何间隔都命中。

换句话说：agent 式的多轮会话恰好落在这套策略的最劣格子里，而这一切从外部
文档完全不可知。同一个网关（opencode zen）上的 mimo-v2.5 却毫无这些毛病，
跨轮 65 秒、176 秒都是全额命中——**缓存行为跟着上游模型厂走，与网关无关，
与客户端无关。**

这段侦探过程留下的方法论，比结论本身更重要：

1. **单变量**：每次实验只动一个变量，构造最小判别对（有/无中段 system、
   流式/非流式、处女链/旧链）；
2. **可复现**：任何"客户端没问题"的断言，必须能用 curl 重放同样的字节复现
   同样的现象；任何"服务端有问题"的断言，必须先穷尽客户端变量；
3. **不轻信基准**：单次大文档问答的评测成绩，不能外推到多轮增量会话——
   它们落在供应商存储策略的两个极端。

## 六、供应商不是抽象接口

上面的发现直接导出一个架构层面的态度：**不要把"OpenAI 兼容 API"当成同一种
东西。** 缓存语义上，供应商至少分三类：

**契约型**——Anthropic 的 cache_control、OpenAI 的 prompt caching、Kimi 的
显式缓存管理。你为缓存写入付费（Anthropic 写入收 1.25x～2x），换来的是明确的
TTL 承诺：付了钱，它就必须在。在这类供应商上，append-only 的字节流就是全部
前提，99.8% 的命中是算术题。

**尽力而为型**——DeepSeek 官方。缓存免费附赠，不收写入费，也就不欠你任何
存储承诺。命中率取决于集群当时的负载和你的流量形态。

**按次计费型**——opencode zen 这类以请求次数为成本单位的网关。缓存不省钱
（可能省延迟），一切"多发请求换命中"的手段在这里都是负收益。

由此,Miyu 的缓存策略分成两层投放：

**普适层**默认开启，因为它们在任何供应商上都只有收益：字节纯度、append-only、
化石化、stub 工具。这些是"把自己的事做对"。

**投放层**默认关闭，因为同一个手段在不同供应商上命运迥异。最典型的是**保温
ping**：会话空闲时，每 20 秒把上一请求的字节前缀原样发一遍（`max_tokens=1`、
非流式），用命中价的成本反复"触碰"缓存，把热窗口人为续住。同链 A/B 实测：
在 DeepSeek 官方上，65 秒空闲后的跨轮命中从 28% 拉到 94.9%，净省约三分之二的
输入成本；在 mimo 上，97.2% 对 97.3%——零收益，还白烧三次请求额度。同一个
开关，一边是救命药，一边是纯浪费。所以它必须默认关，注释里写清适用条件，
由使用者按自己的供应商实测后决定。**尊重差异的方式不是抹平差异，而是把选择
权连同判断依据一起交出去。**

配套的还有**写入宽限**（write grace）：工具循环里如果上一请求刚结束不到
2.5 秒就要发下一个，稍等片刻再发——躲开异步缓存写入的空窗。几百毫秒的延迟，
换回整段前缀的命中，在大上下文下稳赚。

## 七、成本的算术：为什么 coding 是缓存的甜区

把前面所有工作做完之后，会得到一个漂亮的成本结构：**每轮的 miss 是常数。**

新算的部分只剩三样：本轮的用户输入、本轮的化石尾部、上一轮回复的重渲染，
合计约 1.3k token，与上下文规模无关。于是命中率是一个分母不断增长的分数：
40k 上下文时约 97%，116k 实测 99.9%，外推到 300k 就是 99.6% 以上。**上下文
越大，缓存越划算**——这与"上下文大了很贵"的朴素直觉正好相反，前提是你把
字节做纯了。

这也解释了为什么 coding 恰好是缓存的最优场景：一条指令引发几十轮工具调用，
单链、快节奏、纯追加、上下文巨大——每一条都踩在缓存的甜区上。反而是轻量的
闲聊（小上下文、长间隔、频繁新会话）享受不到多少缓存红利。Miyu 同时服务
这两种负载，所以两头的策略都要备着。

## 八、可测量才可优化

最后一条理念关于观测。所有上述结论都来自一行不起眼的日志：

```
prompt cache accounting  prompt_tokens=… cache_read=… fresh=…
```

每个请求一行，绝对值。刻意不用百分比，因为百分比会说谎：一轮正常加入大段
新内容时，百分比下跌，看起来像是缓存坏了，其实前缀命中得好好的。绝对值不需要
解释——`cache_read` 涨没涨，一眼便知。

观测之后是防退化。本批次建立的字节纯度有一个危险的特性：**它退化时毫无症状。**
在 DeepSeek 这类供应商上命中本来就低，字节纯度被某次改动悄悄破坏后，数字
几乎不变；在 mimo 上命中率下跌也没人盯着看。所以下一步是把它变成 CI 门禁：
mock 供应商上断言**第 N 轮请求是第 N-1 轮请求的字节前缀延伸**，一旦有人在
消息组装路径上引入插入、删除或非确定性，测试当场变红。理念要活下去，不能
靠人的自觉，要靠机器的执念。

## 九、报错信息不是证词，是嫌疑人

第五节讲的是「供应商文档不可信」。这一节讲它的孪生兄弟，而且更贴身：
**自家程序报出来的错误信息，同样不可信。**

2026-08-17 这一天连着踩了三次，形态各不相同，共性只有一个——**报错说的原因
不是真原因**：

- 「`start_line is required`」——参数明明传了。模型把整数写成了字符串
  `"1"`，而 `as_u64()` 在 `Value::String` 上返回 `None`，和「没传」是同一个
  返回值，于是必填校验说它缺失。
- 「`Moegirlpedia page not found`」——页面存在，抓取还是 HTTP 200。正文
  609 KB 超过了字节上限，读取整体失败落进 fallback，而那个站点的备用 API 恰好
  被禁用，最后吐出一句和真相毫无关系的话。
- 「图片打印得太大」——尺寸算得完全正确。真正的问题是图片画到了它预留的行数
  之外，后续文字被压在图上。

三次都是先信了报错，然后在错误的抽象层上排查。代价是每次都绕远路。

这件事对 Miyu 有特别的意义，因为 Miyu 的很多参数是**模型**填的，不是人填的。
人填错了会看到报错、会改；模型填错了只会看到一句误导的话，然后换个同样错的
方式重试。所以：

1. **报错要说它真正知道的**。「参数解析失败：期望整数，收到字符串 `"1"`」比
   「必填项缺失」有用一个数量级——它把模型直接推到正确的修法上。
2. **能兜住的就别报错**。工具 schema 自己声明了参数类型，那么模型把数组写成
   JSON 字符串、把整数写成 `"1"`、把布尔写成 Python 风格的 `"False"`，都该在
   注册表分发处按 schema 还原，而不是让每个工具各自去处理。
3. **收口要放在唯一入口上**。同一类问题一天踩三次，前两次都在按调用点打补丁
   ——补完主循环漏了子代理，补完落库漏了回合内的活体路径，补完字符串数组漏了
   对象数组。调用点会增长，补丁跟不上。最后改成两个收口：一个在
   `ChatMessage::assistant`（tool_calls 进入消息的唯一入口），一个在
   `ToolRegistry` 的分发处。
4. **但取证链不能一起净化掉**。落库刻意保留模型发来的原始参数——包括那串半截
   JSON。它是定位根因的唯一线索，洗干净了等于毁掉下次的证据。

还有一条是关于**验证本身**的，这条是当天最狼狈的一次。

有个依赖库会往 stderr 打两行噪声。我做了抑制，然后跑了个渲染公式的测试，数
stderr 得到 0 行，宣布修好。但那个测试**不加抑制也是 0 行**——它渲染的都是
纯数学公式，而会说话的是 Unicode 回退字体，只有 `\text{中文}` 这种才会加载
它。整个"验证"从头到尾没有区分能力，我拿一个恒为绿的测试给自己发了合格证。

用户装上之后噪声照旧。

所以：**"修完之后现象没了"不构成验证。必须先证明不修的时候现象会出现。**
一个不加修复也是绿的测试，加了修复当然还是绿的。做前后对照的成本很低——把
修复临时去掉再跑一遍就行——但省掉它的代价是把没修好的东西当修好的发出去。
这个规矩对回归测试同样适用：新加的用例，退回修复前必须报红，否则它守不住
任何东西。

还有一条是关于**读规范**的。同一天有个终端图片渲染的问题，猜了四轮都没中，
最后一次搜索找到了 kitty 图形协议的原文——「设了页边距之后，只有完全落在页
内的图片才跟着滚动，越界的会被裁剪并留在原地」——机制立刻清楚。四轮猜测的成本，
远高于一次查证。**先读规范，再读代码，最后才轮到推理。**

> 十分之一的价格；而语义的自由，恰恰建立在字节的严格之上。**
